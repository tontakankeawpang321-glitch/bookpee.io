 เอกสารฉบับนี้จัดทำขึ้นโดยได้รับการสนับสนุนด้านเงินทุนจาก
 มูลนิธิวิทยาศาสตร์ แห่งชาติ

ลิขสิทธิ์ (C) 1987 โดยคณะกรรมการบริหารมหาวิทยาลัยอิลลินอยส์ อนุญาตให้ทำสำเนาเอกสารนี้ทั้งหมดหรือบางส่วนได้ โดยมีเงื่อนไขว่าต้องอ้างอิงแหล่งที่มาและต้องระบุลิขสิทธิ์นี้ไว้ในสำเนาทุกฉบับ

เอกสารนี้สันนิษฐานว่าผู้อ่านคุ้นเคยกับการทำงานของเครือข่าย IP แบบง่ายๆ ที่ไม่ได้เชื่อมต่อ (เช่น ระบบ BSD 4.2 สองสามระบบบนสายอีเธอร์เน็ตที่ไม่ได้เชื่อมต่อกับที่อื่น) ภาคผนวก A มีข้อมูลพื้นฐานเพื่อช่วยให้ผู้อ่านเข้าใจถึงจุดนี้ จุดประสงค์คือเพื่อให้ผู้ที่คุ้นเคยกับเครือข่ายแบบง่ายๆ มีความเชี่ยวชาญใน "ธรรมเนียมปฏิบัติ" ของอินเทอร์เน็ตจนถึงจุดที่สามารถเชื่อมต่อเครือข่ายนั้นกับอินเทอร์เน็ตได้อย่างปลอดภัย เอกสารนี้ไม่ใช่คู่มือ แต่ประกอบด้วยคำแนะนำไปยังแหล่งข้อมูล เอกสาร และเคล็ดลับอื่นๆ ที่โดยปกติแล้วไม่ได้มีการบันทึกไว้ เนื่องจากอินเทอร์เน็ตเป็นสภาพแวดล้อมที่มีพลวัต การเปลี่ยนแปลงในเอกสารนี้จึงจะเกิดขึ้นเป็นประจำ ผู้เขียนยินดีรับฟังความคิดเห็นและข้อเสนอแนะ โดยเฉพาะอย่างยิ่งคำศัพท์สำหรับอธิบายศัพท์ (ไม่จำเป็นต้องมีคำจำกัดความ)

ในตอนเริ่มต้น มีเครือข่าย ARPAnet ซึ่งเป็นเครือข่ายทดลองบริเวณกว้างที่เชื่อมต่อโฮสต์และเทอร์มินัลเซิร์ฟเวอร์เข้าด้วยกัน มีการกำหนดขั้นตอนเพื่อควบคุมการจัดสรรที่อยู่และสร้างมาตรฐานโดยสมัครใจสำหรับเครือข่าย เมื่อเครือข่ายบริเวณท้องถิ่น (LAN) แพร่หลายมากขึ้น โฮสต์จำนวนมากจึงกลายเป็นเกตเวย์ไปยังเครือข่ายท้องถิ่น จึงมีการพัฒนาเลเยอร์เครือข่ายเพื่อให้เครือข่ายเหล่านี้สามารถทำงานร่วมกันได้ และเรียกว่า IP (Internet Protocol) เมื่อเวลาผ่านไป กลุ่มอื่นๆ ก็ได้สร้างเครือข่ายระยะไกลที่ใช้ IP (เช่น NASA, NSF, รัฐต่างๆ...) เครือข่ายเหล่านี้ก็สามารถทำงานร่วมกันได้เช่นกันเนื่องจาก IP การรวมกันของเครือข่ายที่ทำงานร่วมกันทั้งหมดเหล่านี้ก็คือ อินเทอร์เน็ต

มีสองกลุ่มหลักที่ทำการวิจัยและจัดหาข้อมูลให้กับอินเทอร์เน็ต (ISI และ SRI) ISI (สถาบันวิทยาศาสตร์สารสนเทศ) ทำงานด้านการวิจัย การกำหนดมาตรฐาน และการจัดสรรทรัพยากรของอินเทอร์เน็ต ในขณะที่ SRI International ให้บริการข้อมูลสำหรับอินเทอร์เน็ต ที่จริงแล้ว หลังจากที่คุณเชื่อมต่อกับอินเทอร์เน็ตแล้ว ข้อมูลส่วนใหญ่ในเอกสารนี้สามารถดึงมาจากศูนย์ข้อมูลเครือข่าย (NIC) ที่ดำเนินการโดย SRI ได้

การใช้งานอินเทอร์เน็ต

แต่ละเครือข่าย ไม่ว่าจะเป็น ARPAnet, NSFnet หรือเครือข่ายระดับภูมิภาค ล้วนมีศูนย์ปฏิบัติการของตนเอง ARPAnet ดำเนินการโดย BBN, Inc. ภายใต้สัญญาจาก DARPA สิ่งอำนวยความสะดวกของพวกเขาเรียกว่า ศูนย์ปฏิบัติการเครือข่าย หรือ NOC มหาวิทยาลัยคอร์เนลดำเนินการ NSFnet ชั่วคราว (เรียกว่า ศูนย์บริการข้อมูลเครือข่าย หรือ NISC) และต่อไปยัง...

ศูนย์ปฏิบัติการเครือข่ายระดับภูมิภาคควรมีสิ่งอำนวยความสะดวกที่คล้ายคลึงกันในการตรวจสอบและเฝ้าระวังความเคลื่อนไหวในส่วนของอินเทอร์เน็ตที่ตนรับผิดชอบ นอกจากนี้ ทุกศูนย์ควรมีความรู้เกี่ยวกับสิ่งที่เกิดขึ้นกับอินเทอร์เน็ตโดยรวม หากเกิดปัญหาขึ้น ขอแนะนำให้ผู้ประสานงานเครือข่ายของมหาวิทยาลัยติดต่อผู้ให้บริการเครือข่ายที่ตนเชื่อมต่อโดยตรง กล่าวคือ หากคุณเชื่อมต่อกับเครือข่ายระดับภูมิภาค (ซึ่งเป็นเกตเวย์ไปยัง NSFnet ซึ่งเชื่อมต่อกับ ARPAnet…) และมีปัญหา คุณควรติดต่อศูนย์ปฏิบัติการเครือข่ายระดับภูมิภาคของคุณ

อาร์เอฟซี

การทำงานภายในของอินเทอร์เน็ตถูกกำหนดโดยชุดเอกสารที่เรียกว่า RFCs (Request for Comments) กระบวนการทั่วไปในการสร้าง RFC คือ ผู้ที่ต้องการกำหนดรูปแบบอย่างเป็นทางการจะเขียนเอกสารอธิบายประเด็นนั้นและส่งไปที่ Jon Postel ([email protected]) เขาจะทำหน้าที่เป็นผู้ตรวจสอบข้อเสนอ จากนั้นผู้ที่เกี่ยวข้องทั้งหมด (ผ่านทางอิเล็กทรอนิกส์) จะแสดงความคิดเห็น อาจมีการแก้ไขหลายครั้ง หากได้รับการยอมรับโดยทั่วไปว่าเป็นความคิดที่ดี ก็จะได้รับหมายเลขและจัดเก็บไว้ใน RFCs

มาตรฐาน RFC สามารถแบ่งออกได้เป็นห้ากลุ่ม ได้แก่ บังคับ แนะนำ กำหนดทิศทาง ให้ข้อมูล และล้าสมัย มาตรฐาน RFC ที่บังคับ (เช่น RFC-791 โปรโตคอลอินเทอร์เน็ต) จะต้องถูกนำไปใช้งานบนโฮสต์ใดๆ ที่เชื่อมต่อกับอินเทอร์เน็ต มาตรฐาน RFC ที่แนะนำโดยทั่วไปจะถูกนำไปใช้งานโดยโฮสต์เครือข่าย การขาดมาตรฐานเหล่านี้ไม่ได้หมายความว่าจะไม่สามารถเข้าถึงอินเทอร์เน็ตได้ แต่Hอาจส่งผลกระทบต่อการใช้งานได้ RFC-793 (โปรโตคอลควบคุมการส่งข้อมูล) เป็นมาตรฐาน RFC ที่แนะนำ มาตรฐาน RFC ที่กำหนดทิศทางนั้นเคยมีการพูดคุยและตกลงกัน แต่การนำไปใช้งานนั้นไม่เคยมีการใช้งานอย่างแพร่หลาย อาจเป็นเพราะความต้องการใช้งานเฉพาะนั้นไม่มากนัก (RFC-937 โปรโตคอลไปรษณีย์) หรือแม้ว่าจะมีศักยภาพทางเทคนิคสูงกว่า แต่ก็ขัดแย้งกับวิธีการอื่นๆ ที่แพร่หลาย (RFC-891 Hello) ขอแนะนำว่าหากไซต์ใดไซต์หนึ่งต้องการฟังก์ชันนี้ ควรดำเนินการตามมาตรฐาน RFC เพื่อให้แน่ใจว่าหากแนวคิดนั้นถึงเวลาที่จะนำมาใช้งานแล้ว การนำไปใช้งานจะเป็นไปตามมาตรฐานบางอย่างและสามารถใช้งานได้โดยทั่วไป เอกสาร RFC เชิงข้อมูลประกอบด้วยข้อมูลข้อเท็จจริงเกี่ยวกับอินเทอร์เน็ตและการทำงานของอินเทอร์เน็ต (RFC-990, หมายเลขที่กำหนด) สุดท้ายนี้ เมื่ออินเทอร์เน็ตและเทคโนโลยีเติบโตขึ้น เอกสาร RFC บางฉบับก็ไม่จำเป็นอีกต่อไป อย่างไรก็ตาม เราไม่ควรละเลยเอกสาร RFC ที่ล้าสมัยเหล่านี้ บ่อยครั้งที่เมื่อมีการเปลี่ยนแปลงเกิดขึ้นกับเอกสาร RFC บางฉบับ ทำให้มีการออกเอกสาร RFC ฉบับใหม่มาแทนที่ฉบับอื่นๆ เอกสาร RFC ฉบับใหม่นั้นจะมีเพียงคำอธิบายและเหตุผลของการเปลี่ยนแปลงเท่านั้น การทำความเข้าใจแบบจำลองที่ใช้เป็นพื้นฐานของระบบทั้งหมดอาจต้องอ่านเอกสาร RFC ฉบับดั้งเดิมและฉบับต่อๆ มาในหัวข้อนั้นๆ

-4-

สำหรับผู้ที่ไม่มีเครือข่าย หรือหากจำนวนเอกสารมีมาก เอกสารของ NIC หลายฉบับมีให้บริการในรูปแบบสิ่งพิมพ์โดยคิดค่าใช้จ่ายเล็กน้อย เอกสารที่มักถูกสั่งซื้อสำหรับเว็บไซต์เริ่มต้นคือ คู่มือรวบรวม RFC ที่สำคัญ การติดต่อทางโทรศัพท์ส่วนใหญ่ใช้สำหรับคำถามหรือปัญหาเกี่ยวกับการเข้าถึงเครือข่าย (ดูภาคผนวก B สำหรับหมายเลขติดต่อทางอีเมล/โทรศัพท์)

ศูนย์บริการเครือข่าย NSFnet

ศูนย์บริการเครือข่าย NSFnet (NNSC) ได้รับทุนสนับสนุนจาก NSF เพื่อให้ความช่วยเหลือเบื้องต้นแก่ผู้ใช้ NSFnet ในกรณีที่พวกเขามีข้อสงสัยหรือพบปัญหาในการใช้งานเครือข่าย NNSC บริหารงานโดย BBN Inc. โดยมี Karen Roubicek ([email protected]) เป็นผู้ประสานงานผู้ใช้ของ NNSC

ปัจจุบัน NNSC มีข้อมูลและเอกสารทั้งในรูปแบบออนไลน์และสิ่งพิมพ์ และมีแผนที่จะเผยแพร่ข่าวสารผ่านทางรายชื่อผู้รับจดหมายของเครือข่าย จดหมายข่าว และรายงานออนไลน์ นอกจากนี้ NNSC ยังดูแลฐานข้อมูลของจุดติดต่อและแหล่งข้อมูลเพิ่มเติมเกี่ยวกับเครือข่ายส่วนประกอบของ NSFnet และศูนย์ซูเปอร์คอมพิวเตอร์อีกด้วย

ผู้ใช้งานปัจจุบันหรือผู้ที่สนใจใช้งาน NSFnet ที่ไม่ทราบว่าจะติดต่อใครหากมีคำถามเกี่ยวกับการใช้งาน NSFnet ควรติดต่อ NNSC NNSC จะตอบคำถามทั่วไป และสำหรับข้อมูลโดยละเอียดเกี่ยวกับส่วนประกอบเฉพาะของอินเทอร์เน็ต NNSC จะช่วยผู้ใช้งานค้นหาผู้ติดต่อที่เหมาะสมเพื่อขอความช่วยเหลือเพิ่มเติม (ภาคผนวก B)

ตัวสะท้อนแสงจดหมาย

วิธีที่คนส่วนใหญ่ติดตามข่าวสารทางโทรทัศน์คือการสมัครรับข้อมูลจากกล่องจดหมายส่งต่อ (mail reflector) กล่องจดหมายส่งต่อเหล่านี้เป็นกล่องจดหมายอิเล็กทรอนิกส์พิเศษ ซึ่งเมื่อได้รับข้อความแล้วจะส่งต่อไปยังกล่องจดหมายอื่นๆ อีกหลายกล่อง โดยจะสร้างกลุ่มสนทนาเกี่ยวกับหัวข้อใดหัวข้อหนึ่งขึ้นมา ผู้สมัครรับข้อมูลแต่ละคนจะเห็นข้อความทั้งหมดที่ส่งต่อโดยกล่องจดหมายส่งต่อ และหากต้องการแสดงความคิดเห็นก็สามารถส่งข้อความไปยังกล่องจดหมายส่งต่อได้...

รูปแบบทั่วไปในการสมัครรับจดหมายข่าวคือ การค้นหาที่อยู่ของตัวสะท้อน (reflector) และเพิ่มสตริง "-REQUEST" ต่อท้ายชื่อกล่องจดหมาย (ไม่ใช่ชื่อโฮสต์) ตัวอย่างเช่น หากคุณต้องการเข้าร่วมในรายชื่อผู้รับจดหมายของ NSFnet ที่สะท้อนโดย [email protected] คุณจะต้องส่งคำขอไปยังที่อยู่ดังกล่าว

-5-

[email protected] นี่อาจเป็นแผนการที่ยอดเยี่ยม แต่ปัญหาคือคุณต้องรู้ก่อนว่ารายชื่อนี้มีอยู่จริง แนะนำว่าหากคุณสนใจ ให้ลองอ่านอีเมลจากรายชื่อใดรายชื่อหนึ่ง (เช่น NSFNET) แล้วคุณอาจจะคุ้นเคยกับการมีอยู่ของรายชื่ออื่นๆ บริการลงทะเบียนสำหรับผู้สะท้อนอีเมลมีให้บริการโดย NIC ในไฟล์ NETINFO:INTEREST-GROUPS-1.TXT, NETINFO:INTEREST-GROUPS-2.TXT และ NETINFO:INTEREST-GROUPS-3.TXT

ระบบกระจายอีเมลของ NSFNET มุ่งเป้าไปที่ผู้ที่สนใจข่าวสารของ NSFnet (เครือข่ายหลัก เครือข่ายระดับภูมิภาค และผู้ปฏิบัติงานในศูนย์เชื่อมต่ออินเทอร์เน็ต) เป็นประจำทุกวัน ข้อความจะถูกส่งมาจากส่วนกลางและส่งเป็นข้อความแยกต่างหากไปยังผู้รับแต่ละราย ซึ่งทำให้เกิดข้อความจำนวนหลายร้อยข้อความบนเครือข่ายบริเวณกว้างซึ่งมีแบนด์วิดท์จำกัดมาก

มีสองวิธีที่มหาวิทยาลัยสามารถเผยแพร่ข่าวสารโดยไม่ทำให้ข้อความเหล่านั้นล้นเครือข่ายบริเวณกว้าง วิธีแรกคือการสะท้อนข้อความภายในมหาวิทยาลัย กล่าวคือ ตั้งค่าตัวสะท้อนบนเครื่องคอมพิวเตอร์ในพื้นที่เพื่อส่งต่อข้อความไปยังรายชื่อผู้รับในมหาวิทยาลัย อีกวิธีหนึ่งคือการสร้างนามแฝงบนเครื่องคอมพิวเตอร์ในมหาวิทยาลัยเพื่อบันทึกข้อความลงในไฟล์บันทึกเกี่ยวกับหัวข้อนั้น ผู้ใช้ในมหาวิทยาลัยที่ต้องการข้อมูลสามารถเข้าถึงไฟล์บันทึกและดูข้อความที่ส่งมาตั้งแต่การเข้าถึงครั้งล่าสุดได้ นอกจากนี้ อาจเลือกให้ผู้ประสานงานเครือข่ายบริเวณกว้างของมหาวิทยาลัยคัดกรองข้อความในทั้งสองกรณีและส่งต่อเฉพาะข้อความที่พิจารณาว่ามีประโยชน์เท่านั้น วิธีการใดวิธีการหนึ่งนี้ช่วยให้สามารถส่งข้อความเดียวไปยังมหาวิทยาลัยได้ ในขณะเดียวกันก็ช่วยให้สามารถกระจายข่าวได้อย่างกว้างขวางภายในมหาวิทยาลัย

การจัดสรรที่อยู่

ก่อนที่เครือข่ายท้องถิ่นจะเชื่อมต่อกับอินเทอร์เน็ตได้ จะต้องได้รับการจัดสรรที่อยู่ IP ที่ไม่ซ้ำกันเสียก่อน ที่อยู่เหล่านี้จะถูกจัดสรรโดย ISI กระบวนการจัดสรรประกอบด้วยการขอแบบฟอร์มใบสมัครจาก ISI (ส่งข้อความไปที่ [email protected] และขอแบบฟอร์มสำหรับที่อยู่เชื่อมต่อ) กรอกแบบฟอร์มนี้ให้ครบถ้วนแล้วส่งกลับไปยัง hostmaster ที่อยู่จะถูกจัดสรรและส่งกลับมาทางอีเมล หรืออาจทำได้โดยการส่งทางไปรษณีย์เช่นกัน (ภาคผนวก B)

ที่อยู่ IP มีความยาว 32 บิต โดยปกติจะเขียนเป็นตัวเลขทศนิยมสี่หลักคั่นด้วยจุด (เช่น 192.17.5.100) แต่ละตัวเลขคือค่าของอ็อกเท็ตจาก 32 บิต ตั้งแต่แรกเริ่มก็เห็นได้ว่าบางเครือข่ายอาจเลือกจัดระเบียบตัวเองแบบแบนราบ (เครือข่ายเดียวที่มีโหนดจำนวนมาก) และบางเครือข่ายอาจจัดระเบียบแบบลำดับชั้น

-6-

(เครือข่ายที่เชื่อมต่อกันจำนวนมาก โดยแต่ละเครือข่ายมีโหนดน้อยลงและมีแกนหลัก) เพื่อรองรับกรณีเหล่านี้ จึงมีการแบ่งประเภทที่อยู่เป็นเครือข่ายคลาส A, B และ C การแบ่งประเภทนี้เกี่ยวข้องกับการตีความอ็อกเท็ต เครือข่ายคลาส A มีอ็อกเท็ตแรกเป็นที่อยู่เครือข่าย และอีกสามอ็อกเท็ตที่เหลือเป็นที่อยู่โฮสต์บนเครือข่ายนั้น ที่อยู่คลาส C มีสามอ็อกเท็ตเป็นที่อยู่เครือข่ายและหนึ่งอ็อกเท็ตเป็นที่อยู่โฮสต์ คลาส B แบ่งออกเป็นสองส่วนเท่าๆ กัน ดังนั้นจึงมีพื้นที่ที่อยู่สำหรับเครือข่ายขนาดใหญ่จำนวนหนึ่ง เครือข่ายขนาดกลางจำนวนหนึ่ง และเครือข่ายขนาดเล็กจำนวนมาก บิตสองบิตบนสุดในอ็อกเท็ตแรกถูกเข้ารหัสเพื่อบอกรูปแบบที่อยู่ เครือข่ายคลาส A ทั้งหมดได้รับการจัดสรรแล้ว ดังนั้นจึงต้องเลือกระหว่างคลาส B และคลาส C เมื่อทำการสั่งซื้อ (นอกจากนี้ยังมีรูปแบบคลาส D (มัลติแคสต์) และ E (ทดลอง) ที่อยู่มัลติแคสต์น่าจะมีการใช้งานมากขึ้นในอนาคตอันใกล้ แต่ปัจจุบันยังไม่ค่อยได้ใช้)

ในอดีต เว็บไซต์ที่ต้องการที่อยู่เครือข่ายหลายรายการจะขอที่อยู่แยกต่างหากหลายรายการ (โดยปกติคือ Class C) เนื่องจากซอฟต์แวร์ส่วนใหญ่ที่มีอยู่ (โดยเฉพาะ 4.2BSD) ไม่สามารถจัดการกับที่อยู่แบบซับเน็ตได้ ข้อมูลเกี่ยวกับวิธีการเข้าถึงเครือข่ายเฉพาะ (ข้อมูลการกำหนดเส้นทาง) จะต้องถูกจัดเก็บไว้ในเกตเวย์อินเทอร์เน็ตและสวิตช์แพ็กเก็ต โหนดเหล่านี้บางส่วนมีขีดจำกัดในการจัดเก็บและแลกเปลี่ยนข้อมูลการกำหนดเส้นทาง (จำกัดประมาณ 300 เครือข่าย) ดังนั้นจึงแนะนำว่าวิทยาเขตใด ๆ ควรประกาศ (แจ้งให้ทางอินเทอร์เน็ตทราบ) หมายเลขเครือข่ายแยกต่างหากไม่เกินสองหมายเลข

หากมหาวิทยาลัยคาดว่าจะถูกจำกัดด้วยข้อกำหนดนี้ ควรพิจารณาการแบ่งซับเน็ต การแบ่งซับเน็ต (RFC-932) ช่วยให้สามารถประกาศที่อยู่หนึ่งไปยังอินเทอร์เน็ตและใช้ชุดที่อยู่ต่างๆ ภายในมหาวิทยาลัยได้ โดยพื้นฐานแล้ว จะมีการกำหนดมาสก์ซึ่งช่วยให้เครือข่ายสามารถแยกแยะระหว่างส่วนเครือข่ายและส่วนโฮสต์ของที่อยู่ได้ การใช้มาสก์ที่แตกต่างกันระหว่างอินเทอร์เน็ตและภายในมหาวิทยาลัย จะทำให้สามารถตีความที่อยู่ได้หลายวิธี ตัวอย่างเช่น หากมหาวิทยาลัยต้องการเครือข่ายภายในสองเครือข่ายและมีที่อยู่ 32,000 ที่อยู่ขึ้นต้นด้วย 128.174.XX (ที่อยู่คลาส B) ที่จัดสรรไว้ให้ มหาวิทยาลัยสามารถจัดสรร 128.174.5.X ให้กับส่วนหนึ่งของมหาวิทยาลัยและ 128.174.10.X ให้กับอีกส่วนหนึ่งได้ โดยการประกาศ 128.174 ไปยังอินเทอร์เน็ตด้วยซับเน็ตมาสก์ FF.FF.00.00 อินเทอร์เน็ตจะถือว่าที่อยู่ทั้งสองนี้เป็นที่อยู่เดียวกัน ภายในวิทยาเขตจะใช้มาสก์ FF.FF.FF.00 ซึ่งทำให้วิทยาเขตสามารถจัดการที่อยู่เหล่านั้นเป็นหน่วยแยกต่างหากได้ (ในความเป็นจริง คุณไม่ได้ส่งซับเน็ตมาสก์ FF.FF.00.00 ไปยังอินเทอร์เน็ต ความหมายของอ็อกเท็ตนั้นแฝงอยู่ในตัวมันเองอยู่แล้วว่าเป็นที่อยู่คลาส B) จำเป็นต้องเตือนไว้ด้วยว่า ไม่ใช่ทุกระบบที่จะรู้วิธีการทำซับเน็ต ระบบ 4.2BSD บางระบบต้องการซอฟต์แวร์เพิ่มเติม ระบบ 4.3BSD ทำซับเน็ตตามที่เปิดตัวไว้แล้ว อุปกรณ์อื่นๆ อาจมีปัญหา

-7-

และระบบปฏิบัติการแต่ละระบบก็มีปัญหาในการจัดการกับซับเน็ตแตกต่างกันไป บ่อยครั้งที่เครื่องเหล่านี้สามารถใช้เป็นลีฟในเครือข่ายได้ แต่ไม่สามารถใช้ทำหน้าที่เป็นเกตเวย์ภายในส่วนของเครือข่ายที่แบ่งเป็นซับเน็ตได้ เมื่อเวลาผ่านไปและระบบต่างๆ หันมาใช้ 4.3BSD มากขึ้น ปัญหาเหล่านี้ก็จะค่อยๆ หายไป

ที่ผ่านมาเคยมีความสับสนเกี่ยวกับรูปแบบของที่อยู่ IP แบบบรอดแคสต์ บางเครื่องใช้ที่อยู่ที่เป็นเลขศูนย์ทั้งหมดเพื่อหมายถึงการบรอดแคสต์ และบางเครื่องใช้ที่เป็นเลขหนึ่งทั้งหมด ซึ่งทำให้เกิดความสับสนเมื่อเครื่องทั้งสองประเภทเชื่อมต่ออยู่ในเครือข่ายเดียวกัน ปัจจุบันจึงมีการนำรูปแบบที่อยู่บรอดแคสต์ที่เป็นเลขหนึ่งทั้งหมดมาใช้เพื่อยุติความสับสนนี้ บางระบบ (เช่น 4.2 BSD) อนุญาตให้เลือกรูปแบบของที่อยู่บรอดแคสต์ได้ หากระบบอนุญาตให้เลือกรูปแบบนี้ ควรระมัดระวังในการเลือกรูปแบบที่เป็นเลขหนึ่งทั้งหมด (รายละเอียดอยู่ใน RFC-1009 และ RFC-1010)

ปัญหาเกี่ยวกับอินเทอร์เน็ต

อินเทอร์เน็ตมีปัญหาอยู่หลายประการ วิธีแก้ปัญหาเหล่านี้มีตั้งแต่การเปลี่ยนแปลงซอฟต์แวร์ไปจนถึงโครงการวิจัยระยะยาว ปัญหาสำคัญบางประการมีรายละเอียดดังต่อไปนี้:

จำนวนเครือข่าย

เมื่ออินเทอร์เน็ตได้รับการออกแบบครั้งแรกนั้น ตั้งใจให้มีเครือข่ายเชื่อมต่อประมาณ 50 เครือข่าย แต่ด้วยการเติบโตอย่างรวดเร็วของเครือข่าย ปัจจุบันจำนวนเครือข่ายเพิ่มขึ้นเกือบ 300 เครือข่าย ซอฟต์แวร์ในกลุ่มเกตเวย์ที่สำคัญ (เรียกว่าเกตเวย์หลักของ ARPAnet) ไม่สามารถส่งผ่านหรือจัดเก็บข้อมูลได้มากกว่าจำนวนนั้นมากนัก ในระยะสั้น การจัดสรรและการเขียนโค้ดใหม่ของเกตเวย์หลักได้ช่วยเพิ่มจำนวนเครือข่ายขึ้นเล็กน้อย ภายในฤดูร้อนปี 1988 เกตเวย์หลัก PDP-11 ในปัจจุบันจะถูกแทนที่ด้วยเกตเวย์ BBN Butterfly ซึ่งจะช่วยแก้ปัญหานี้ได้

ปัญหาการกำหนดเส้นทาง

นอกจากปริมาณข้อมูลมหาศาลที่จำเป็นสำหรับการส่งแพ็กเก็ตไปยังเครือข่ายจำนวนมากแล้ว ยังมีปัญหามากมายเกี่ยวกับการอัปเดต ความเสถียร และความเหมาะสมที่สุดของอัลกอริธึมการกำหนดเส้นทาง มีการวิจัยมากมายในด้านนี้ แต่ทางออกที่ดีที่สุดสำหรับปัญหาการกำหนดเส้นทางเหล่านี้ยังคงต้องใช้เวลาอีกหลายปี ในกรณีส่วนใหญ่ การกำหนดเส้นทางที่เรามีอยู่ในปัจจุบันใช้งานได้ แต่ไม่เหมาะสมที่สุดและบางครั้งก็คาดเดาไม่ได้

-8-

ปัญหาเรื่องความไว้วางใจ

เกตเวย์ทำหน้าที่แลกเปลี่ยนข้อมูลการกำหนดเส้นทางเครือข่าย ปัจจุบัน เกตเวย์ส่วนใหญ่ยอมรับโดยไม่มีการตรวจสอบอย่างละเอียดว่าข้อมูลเกี่ยวกับสถานะของเครือข่ายนั้นถูกต้อง ในอดีต นี่ไม่ใช่ปัญหาใหญ่ เนื่องจากเกตเวย์ส่วนใหญ่อยู่ภายใต้หน่วยงานบริหารเดียวกัน (DARPA) แต่ในปัจจุบัน มีเครือข่ายบริเวณกว้างหลายเครือข่ายภายใต้การบริหารที่แตกต่างกัน เกตเวย์ที่ผิดปกติในเครือข่ายอาจทำให้ระบบอินเทอร์เน็ตล่มได้ ขณะนี้กำลังมีการออกแบบเพื่อแก้ปัญหาทั้งเรื่องเกตเวย์ทำงานผิดปกติ และเพื่อให้มีข้อมูลที่เพียงพอสำหรับการกำหนดเส้นทางข้อมูลระหว่างเครือข่ายที่เชื่อมต่อหลายเครือข่าย (เครือข่ายหลายโฮม) อย่างเหมาะสม

ความจุและความแออัด

หลายส่วนของเครือข่าย ARPAnet มีความหนาแน่นสูงมากในช่วงเวลาที่มีการใช้งานมากที่สุดของวัน มีการวางแผนที่จะเพิ่มลิงก์เพิ่มเติมเพื่อบรรเทาปัญหาความหนาแน่นนี้ แต่การดำเนินการจะใช้เวลาหลายเดือน

-9- การกำหนดเส้นทาง

การกำหนดเส้นทาง (Routing) คืออัลกอริทึมที่เครือข่ายใช้ในการส่งแพ็กเก็ตจากต้นทางไปยังปลายทาง เพื่อให้เข้าใจปัญหาได้ดีขึ้น ลองนึกภาพเด็กเล็ก ๆ พยายามหาโต๊ะในร้านอาหาร จากมุมมองของผู้ใหญ่ โครงสร้างของห้องอาหารสามารถมองเห็นได้ชัดเจนและสามารถเลือกเส้นทางที่ดีที่สุดได้อย่างง่ายดาย แต่สำหรับเด็กแล้ว พวกเขาต้องเผชิญกับเส้นทางมากมายระหว่างโต๊ะ ซึ่งยากที่จะแยกแยะได้ว่าเส้นทางไหนดี หรือแม้แต่เส้นทางที่ดีที่สุดไปยังจุดหมายปลายทาง***

อาจจำเป็นต้องอธิบายเพิ่มเติมอีกเล็กน้อย เกตเวย์ IP (หรือเรียกให้ถูกต้องกว่าคือเราเตอร์) คืออุปกรณ์ที่มีการเชื่อมต่อกับเครือข่ายหลายเครือข่ายและส่งต่อข้อมูลระหว่างเครือข่ายเหล่านั้น เกตเวย์จะตัดสินใจว่าจะส่งแพ็กเก็ตอย่างไรโดยพิจารณาจากข้อมูลในส่วนหัว IP ของแพ็กเก็ตและสถานะของเครือข่าย อินเทอร์เฟซแต่ละตัวบนเราเตอร์จะมีที่อยู่เฉพาะที่เหมาะสมกับเครือข่ายที่เชื่อมต่ออยู่ ข้อมูลในส่วนหัว IP ที่ใช้เป็นหลักคือที่อยู่ปลายทาง ข้อมูลอื่นๆ (เช่น ประเภทของบริการ) มักถูกละเลยในขณะนี้ สถานะของเครือข่ายถูกกำหนดโดยเราเตอร์ที่ส่งต่อข้อมูลระหว่างกัน การกระจายของฐานข้อมูล (สิ่งที่แต่ละโหนดรู้) รูปแบบของการอัปเดต และตัวชี้วัดที่ใช้ในการวัดคุณค่าของการเชื่อมต่อ คือพารามิเตอร์ที่กำหนดลักษณะของโปรโตคอลการกำหนดเส้นทาง

ภายใต้อัลกอริทึมบางประเภท โหนดแต่ละโหนดในเครือข่ายจะมีความรู้ที่สมบูรณ์เกี่ยวกับสถานะของเครือข่าย (อัลกอริทึมสำหรับผู้ใหญ่) ซึ่งหมายความว่าโหนดเหล่านั้นต้องมีพื้นที่จัดเก็บข้อมูลภายในเครื่องจำนวนมากและมี CPU เพียงพอที่จะค้นหาตารางขนาดใหญ่ในเวลาอันสั้น (โปรดจำไว้ว่าต้องทำเช่นนี้สำหรับทุกแพ็กเก็ต) นอกจากนี้ การอัปเดตเส้นทางมักจะประกอบด้วยการเปลี่ยนแปลงเฉพาะข้อมูลที่มีอยู่แล้วเท่านั้น (มิฉะนั้นคุณจะต้องใช้ความจุของเครือข่ายจำนวนมากในการส่งข้อมูลอัปเดตเส้นทางขนาดเมกะไบต์ไปมา) อัลกอริทึมประเภทนี้มีปัญหาหลายประการ เนื่องจากวิธีเดียวที่จะส่งข้อมูลเส้นทางไปได้คือผ่านเครือข่าย และเวลาในการแพร่กระจายนั้นไม่น้อยเลย มุมมองของเครือข่ายที่แต่ละโหนดจึงเป็นมุมมองทางประวัติศาสตร์ที่ถูกต้องของเครือข่ายในช่วงเวลาต่างๆ ในอดีต (อัลกอริทึมสำหรับผู้ใหญ่ แต่แทนที่จะมองไปที่บริเวณรับประทานอาหารโดยตรง ให้มองไปที่ภาพถ่ายของห้องรับประทานอาหาร เราอาจเลือกเส้นทางที่ดีที่สุดแล้วพบว่ามีรถเข็นเข้ามาขวางทางหลังจากถ่ายภาพไปแล้ว) ความไม่สอดคล้องกันเหล่านี้อาจทำให้เกิดเส้นทางวนซ้ำ (เรียกว่าวงวนการกำหนดเส้นทาง) ซึ่งเมื่อแพ็กเก็ตเข้ามาแล้ว จะถูกส่งไปตามเส้นทางปิดจนกว่าค่าเวลาในการคงอยู่ (TTL) จะหมดอายุและถูกทิ้งไป

อัลกอริทึมอื่นๆ อาจรู้จักเพียงส่วนย่อยของเครือข่ายเท่านั้น เพื่อป้องกันลูปในโปรโตคอลเหล่านี้ โดยทั่วไปจึงมักใช้ในเครือข่ายแบบลำดับชั้น พวกมันรู้จักพื้นที่ของตนเองอย่างสมบูรณ์ แต่ในการออกจากพื้นที่นั้น พวกมันจะต้องไปยังจุดใดจุดหนึ่งโดยเฉพาะ (เกตเวย์เริ่มต้น) โดยทั่วไปแล้วจะใช้ในเครือข่ายขนาดเล็ก (เช่น เครือข่ายในมหาวิทยาลัย เครือข่ายระดับภูมิภาค…)

-10-

โปรโตคอลการกำหนดเส้นทางที่ใช้งานอยู่ในปัจจุบัน:

แบบคงที่ (ไม่มีตารางโปรโตคอล/การกำหนดเส้นทางเริ่มต้น)

อย่าหัวเราะ นี่อาจเป็นวิธีที่เชื่อถือได้มากที่สุด ใช้งานง่ายที่สุด และมีโอกาสน้อยที่สุดที่จะทำให้เกิดปัญหาสำหรับเครือข่ายขนาดเล็กหรือจุดเชื่อมต่อบนอินเทอร์เน็ต นอกจากนี้ยังเป็นวิธีเดียวที่มีให้ใช้งานในบางชุด CPU และระบบปฏิบัติการ หากโฮสต์เชื่อมต่อกับอีเธอร์เน็ตที่มีเกตเวย์เพียงตัวเดียว ควรตั้งค่าเกตเวย์นั้นเป็นเกตเวย์เริ่มต้นสำหรับโฮสต์และไม่ต้องกำหนดเส้นทางอื่น (แน่นอนว่าเกตเวย์นั้นอาจส่งข้อมูลการเข้าถึงไปยังอีกฝั่งหนึ่งได้)

ข้อควรระวังอย่างหนึ่งคือ ควรใช้เส้นทางคงที่ (static routes) ในเครือข่ายที่มีการกำหนดเส้นทางแบบไดนามิก (dynamic routing) อยู่ด้วยความระมัดระวังเป็นอย่างยิ่ง เราเตอร์ที่ส่งข้อมูลแบบไดนามิกอาจเกิดความสับสนจากเส้นทางแบบไดนามิกและเส้นทางคงที่ที่ขัดแย้งกัน หากโฮสต์ของคุณอยู่บนเครือข่ายอีเธอร์เน็ตที่มีเราเตอร์หลายตัวเชื่อมต่อกับเครือข่ายอื่น ๆ และเราเตอร์เหล่านั้นกำลังกำหนดเส้นทางแบบไดนามิกกันเอง โดยทั่วไปแล้ว การเข้าร่วมในการกำหนดเส้นทางแบบไดนามิกจะดีกว่าการใช้เส้นทางคงที่

RIP เป็นโปรโตคอลการกำหนดเส้นทางที่ใช้ XNS (Xerox Network System) ซึ่งดัดแปลงมาใช้กับเครือข่าย IP มีการใช้งานในเราเตอร์หลายตัว (Proteon, Cisco, UB…) และระบบ BSD Unix หลายระบบ ระบบ BSD มักจะรันโปรแกรมที่เรียกว่า "routed" เพื่อแลกเปลี่ยนข้อมูลกับระบบอื่นๆ ที่ใช้ RIP RIP ทำงานได้ดีที่สุดสำหรับเครือข่ายที่มีขนาดเล็กและลิงก์มีความเร็วเท่ากัน เหตุผลก็คือ ตัวชี้วัดที่ใช้ในการพิจารณาว่าเส้นทางใดดีที่สุดคือจำนวนฮอป ฮอปคือการเดินทางผ่านเกตเวย์ ดังนั้น เครื่องทุกเครื่องที่อยู่ในอีเธอร์เน็ตเดียวกันจึงอยู่ห่างกันเป็นศูนย์ฮอป หากเราเตอร์เชื่อมต่อเครือข่ายสองเครือข่ายโดยตรง เครื่องที่อยู่อีกฝั่งของเราเตอร์จะอยู่ห่างกันหนึ่งฮอป… เนื่องจากข้อมูลการกำหนดเส้นทางถูกส่งผ่านเกตเวย์ เกตเวย์จะเพิ่มจำนวนฮอปขึ้นหนึ่งเพื่อให้มีความสม่ำเสมอทั่วทั้งเครือข่าย เส้นผ่านศูนย์กลางของเครือข่ายถูกกำหนดให้เป็นจำนวนฮอปที่ใหญ่ที่สุดที่เป็นไปได้ภายในเครือข่าย น่าเสียดายที่ในโปรโตคอล RIP ค่าจำนวนฮอปที่ 16 ถูกกำหนดให้เป็นค่าอนันต์ ซึ่งหมายความว่าลิงก์นั้นใช้งานไม่ได้ ดังนั้น RIP จะไม่อนุญาตให้โฮสต์ที่อยู่ห่างกันมากกว่า 15 เกตเวย์ในพื้นที่ RIP สื่อสารกันได้

ปัญหาอีกอย่างของตัวชี้วัดจำนวนฮอปคือ หากลิงก์มีความเร็วต่างกัน ความแตกต่างนั้นจะไม่ถูกวัด

-11-

สะท้อนให้เห็นในจำนวนฮอป ดังนั้นลิงก์ดาวเทียมแบบหนึ่งฮอป (ที่มีความล่าช้า 0.5 วินาที) ที่ความเร็ว 56 กิโลไบต์ จะถูกใช้แทนการเชื่อมต่อ T1 แบบสองฮอป ความแออัดสามารถมองได้ว่าเป็นการลดลงของประสิทธิภาพของลิงก์ ดังนั้นเมื่อลิงก์แออัดมากขึ้น RIP ก็ยังคงรู้ว่ามันเป็นเส้นทางที่มีจำนวนฮอปที่ดีที่สุด และจะทำให้เกิดความแออัดมากขึ้นไปอีกโดยการส่งแพ็กเก็ตจำนวนมากขึ้นไปยังคิวสำหรับลิงก์นั้น

โปรโตคอลนี้ยังไม่มีการจัดทำเอกสารอย่างละเอียด กลุ่มคนกลุ่มหนึ่งกำลังทำงานเพื่อจัดทำ RFC เพื่อกำหนดนิยามของ RIP ในปัจจุบัน และเพิ่มเติมส่วนเสริมบางอย่างเพื่อให้สามารถรับมือกับเครือข่ายขนาดใหญ่ได้ดียิ่งขึ้น ในขณะนี้ เอกสารที่ดีที่สุดสำหรับ RIP ดูเหมือนจะเป็นโค้ดสำหรับ BSD "routed"

เส้นทาง

โปรแกรม ROUTED ซึ่งทำหน้าที่ RIP สำหรับระบบ 4.2BSD มีตัวเลือกมากมาย หนึ่งในตัวเลือกที่ใช้บ่อยที่สุดคือ "routed -q" (โหมดเงียบ) ซึ่งหมายถึงการรับฟังข้อมูล RIP แต่จะไม่ส่งออกไป ตัวเลือกนี้จะถูกใช้โดยเครื่องในเครือข่ายที่มีเกตเวย์ที่รองรับ RIP หลายตัว ช่วยให้โฮสต์สามารถกำหนดได้ว่าเกตเวย์ใดดีที่สุด (ในแง่ของจำนวนฮอป) ในการเข้าถึงเครือข่ายที่อยู่ห่างไกล (แน่นอนว่าคุณอาจต้องการมีเกตเวย์เริ่มต้นเพื่อป้องกันการต้องส่งผ่านที่อยู่ทั้งหมดที่รู้จักบนอินเทอร์เน็ตด้วย RIP)

มีสองวิธีในการเพิ่มเส้นทางคงที่ลงใน "routed" คือ ไฟล์ "/etc/gateways" และคำสั่ง "route add" เส้นทางคงที่นั้นมีประโยชน์หากคุณรู้วิธีเข้าถึงเครือข่ายที่อยู่ห่างไกล แต่คุณไม่ได้รับเส้นทางนั้นผ่าน RIP โดยส่วนใหญ่แล้ว คำสั่ง "route add" จะเป็นที่นิยมมากกว่า เหตุผลก็คือ คำสั่งนี้จะเพิ่มเส้นทางลงในตารางเส้นทางของเครื่องนั้น แต่จะไม่ส่งออกผ่าน RIP ไฟล์ "/etc/gateways" มีลำดับความสำคัญเหนือกว่าข้อมูลเส้นทางใดๆ ที่ได้รับผ่านการอัปเดต RIP นอกจากนี้ยังถูกส่งออกไปเป็นข้อเท็จจริงในการอัปเดต RIP ที่สร้างโดยโฮสต์โดยไม่มีข้อสงสัย ดังนั้นหากเกิดข้อผิดพลาดในไฟล์ "/etc/gateways" ข้อผิดพลาดนั้นจะแพร่กระจายไปยังพื้นที่ RIP อย่างรวดเร็วและอาจทำให้เครือข่ายล่มได้

ปัญหาอย่างหนึ่งของการกำหนดเส้นทาง (routed) คือ คุณควบคุมได้น้อยมากว่าอะไรจะถูกส่งออกไปและอะไรจะไม่ถูกส่งออกไป หลายครั้งในเครือข่ายขนาดใหญ่ที่ส่วนต่างๆ ของเครือข่ายอยู่ภายใต้การควบคุมดูแลที่แตกต่างกัน คุณอาจต้องการส่งต่อเฉพาะเครือข่าย RIP ที่คุณได้รับจาก RIP และคุณรู้ว่าเหมาะสมเท่านั้น เพื่อป้องกันไม่ให้บุคคลอื่นเพิ่มที่อยู่ IP ลงในเครือข่ายซึ่งอาจผิดกฎหมาย และป้องกันไม่ให้คุณต้องรับผิดชอบในการส่งต่อที่อยู่เหล่านั้นไปยังอินเทอร์เน็ต

-12-

การตรวจสอบความสมเหตุสมผลประเภทต่างๆ ไม่สามารถใช้งานได้กับ "routed" ทำให้ใช้งานได้ แต่ไม่เพียงพอสำหรับเครือข่ายขนาดใหญ่

สวัสดี (RFC-891)

Hello เป็นโปรโตคอลการกำหนดเส้นทางที่ได้รับการออกแบบและนำไปใช้ในเราเตอร์ซอฟต์แวร์ทดลองที่เรียกว่า "Fuzzball" ซึ่งทำงานบน PDP-11 แม้ว่าจะยังไม่เป็นที่นิยมใช้กันอย่างแพร่หลาย แต่ก็เป็นโปรโตคอลการกำหนดเส้นทางที่ใช้ในปัจจุบันบนโครงข่ายหลักของ NSFnet ข้อมูลที่ถ่ายโอนระหว่างโหนดนั้นคล้ายกับ RIP (รายการเครือข่ายและค่าเมตริก) อย่างไรก็ตาม ค่าเมตริกที่ใช้คือมิลลิวินาทีของความล่าช้า ทำให้ Hello สามารถใช้งานได้บนเครือข่ายที่มีความเร็วลิงก์แตกต่างกัน และทำงานได้ดีกว่าในสถานการณ์ที่มีการจราจรหนาแน่น

หนึ่งในผลพลอยได้ที่น่าสนใจที่สุดของเครือข่ายที่ใช้ Hello คือความสามารถในการรักษาเวลาที่ดีเยี่ยม หากคุณพิจารณาปัญหาการวัดความล่าช้าบนลิงก์เพื่อใช้เป็นตัวชี้วัด คุณจะพบว่ามันไม่ใช่เรื่องง่ายที่จะทำ คุณไม่สามารถวัดเวลาไป-กลับได้ เนื่องจากลิงก์ขาเข้าอาจมีความแออัดมากกว่า มีความเร็วที่แตกต่างกัน หรืออาจไม่มีอยู่เลย การที่แต่ละโหนดในเครือข่ายมีตัวรับสัญญาณ WWV (มาตรฐานเวลาวิทยุระดับประเทศ) ในตัวนั้นไม่สามารถทำได้จริง ดังนั้น คุณต้องออกแบบอัลกอริทึมเพื่อส่งผ่านเวลาไปมาระหว่างโหนดต่างๆ ผ่านลิงก์เครือข่าย ซึ่งความล่าช้าในการส่งข้อมูลนั้นสามารถประมาณได้เท่านั้น เราเตอร์ Hello ทำเช่นนี้ และในเครือข่ายระดับประเทศสามารถรักษาเวลาที่ซิงโครไนซ์ได้ภายในมิลลิวินาที

โปรโตคอลเกตเวย์ภายนอก (EGP RFC-904)

EGP ไม่ใช่โปรโตคอลการกำหนดเส้นทางโดยตรง แต่เป็นโปรโตคอลการเข้าถึงได้ มันบอกเพียงว่าสามารถเข้าถึงเครือข่ายผ่านเกตเวย์ที่กำหนดได้หรือไม่ ไม่ได้บอกว่าการเชื่อมต่อดีแค่ไหน มันเป็นมาตรฐานที่เกตเวย์ไปยังเครือข่ายท้องถิ่นแจ้งให้ ARPAnet ทราบถึงเครือข่ายที่พวกเขาสามารถเข้าถึงได้ EGP มีค่าเมตริกที่ส่งผ่านกัน แต่การใช้งานยังไม่ได้รับการกำหนดมาตรฐานอย่างเป็นทางการ ค่าทั่วไปคือ 1 ถึง 8 ซึ่งเป็นค่าความดีของลิงก์โดยประมาณที่เกตเวย์ DDN ภายในเข้าใจ ยิ่งค่าน้อยยิ่งดี และค่า 8 หมายถึงเข้าถึงไม่ได้ ข้อจำกัดของโปรโตคอลทำให้ไม่สามารถแยกแยะระหว่าง 1 กับ 2, 3 กับ 4… ได้ ดังนั้นการใช้งานเป็นเมตริกจึงมีเพียงสามค่าและเข้าถึงไม่ได้ ภายใน NSFnet ค่าที่ใช้คือ 1, 3 และเข้าถึงไม่ได้ เราเตอร์หลายตัวใช้ EGP ดังนั้นจึงสามารถใช้เป็นเกตเวย์ ARPAnet ได้

-13-

ประตูรั้ว

ดังนั้น เราจึงมีเครือข่ายระดับภูมิภาคและระดับมหาวิทยาลัยที่สื่อสารกันด้วยโปรโตคอล RIP เครือข่ายหลัก NSFnet สื่อสารด้วยโปรโตคอล Hello และ DDN สื่อสารด้วยโปรโตคอล EGP พวกมันทำงานร่วมกันได้อย่างไร? ในตอนแรกมีการใช้การกำหนดเส้นทางแบบคงที่ (static routing) ซึ่งประกอบเข้ากับซอฟต์แวร์ Fuzzball ที่กำหนดค่าสำหรับแต่ละไซต์ ปัญหาของการใช้การกำหนดเส้นทางแบบคงที่ในส่วนกลางของเครือข่ายคือ มันจะกระจายไปยังอินเทอร์เน็ตไม่ว่าจะเป็นไปได้หรือไม่ก็ตาม ดังนั้น หากเครือข่ายเข้าถึงไม่ได้และคุณพยายามเข้าถึง การกำหนดเส้นทางแบบไดนามิก (dynamic routing) จะแจ้งว่าเครือข่ายเข้าถึงไม่ได้ทันที ในขณะที่การกำหนดเส้นทางแบบคงที่ เราเตอร์จะคิดว่าสามารถเข้าถึงเครือข่ายได้และจะพยายามต่อไปจนกว่าแอปพลิเคชันจะยอมแพ้ (ภายใน 2 นาทีขึ้นไป) มาร์ค เฟดอร์ จากมหาวิทยาลัยคอร์เนลล์ ([email protected]) พยายามแก้ปัญหาเหล่านี้ด้วยการใช้คำว่า "gated" แทนคำว่า "routed"

การสื่อสารแบบ "Gated" จะสื่อสารแบบ RIP กับโฮสต์ที่พูด RIP, EGP กับผู้พูด EGP และ Hello กับผู้รับ Hello อุปกรณ์เหล่านี้มักจะอยู่บนเครือข่าย Ethernet เดียวกัน แต่โชคดี (หรือโชคร้าย) ที่ไม่สามารถเข้าใจความคิดเห็นของกันและกันได้ นอกจากนี้ ภายใต้การควบคุมไฟล์การกำหนดค่า ยังสามารถกรองการแปลงได้ ตัวอย่างเช่น สามารถสร้างการกำหนดค่าที่ระบุว่าให้ประกาศเครือข่าย RIP ผ่าน Hello เฉพาะเมื่อระบุไว้ในรายการและสามารถเข้าถึงได้ผ่านการออกอากาศ RIP เท่านั้น ซึ่งหมายความว่าหากมีเครือข่ายที่ไม่ได้รับอนุญาตปรากฏในพื้นที่ RIP ของไซต์ของคุณ เครือข่ายนั้นจะไม่ถูกส่งต่อไปยังฝั่ง Hello นอกจากนี้ยังมีตัวเลือกการกำหนดค่าสำหรับการกำหนดเส้นทางแบบคงที่และการตั้งชื่อเกตเวย์ที่เชื่อถือได้

นี่อาจฟังดูเหมือนสิ่งที่ดีที่สุดนับตั้งแต่มีการคิดค้นขนมปังหั่นเป็นแผ่น แต่มีข้อควรระวังเรื่องการแปลงหน่วยวัด RIP วัดเป็นจำนวนฮอป Hello วัดเป็นมิลลิวินาที และ EGP ใช้ตัวเลขเล็กๆ ที่กำหนดขึ้นเอง คำถามสำคัญคือ หนึ่งมิลลิวินาทีเท่ากับกี่ฮอป และเลข 3 ใน EGP เท่ากับกี่มิลลิวินาที... นอกจากนี้ โปรดจำไว้ว่า ค่าอนันต์ (เข้าถึงไม่ได้) คือ 16 สำหรับ RIP ประมาณ 30000 สำหรับ Hello และ 8 สำหรับ DDN ด้วย EGP การทำให้หน่วยวัดเหล่านี้ทำงานร่วมกันได้ดีนั้นไม่ใช่เรื่องง่าย หากทำไม่ถูกต้องและคุณแปลง RIP 16 เป็น EGP 6 ทุกคนใน ARPAnet จะยังคงคิดว่าเกตเวย์ของคุณสามารถเข้าถึงสิ่งที่เข้าถึงไม่ได้และจะส่งแพ็กเก็ตทุกแพ็กเก็ตในโลกมาที่คุณ ด้วยเหตุผลเหล่านี้ มาร์คจึงขอให้คุณปรึกษาหารือกับเขาอย่างใกล้ชิดเมื่อกำหนดค่าและใช้งาน "เกตเวย์"

-14-

"ชื่อ"

การกำหนดเส้นทางทั้งหมดในเครือข่ายทำได้โดยใช้ที่อยู่ IP ที่เชื่อมโยงกับแพ็กเก็ต เนื่องจากมนุษย์จำที่อยู่เช่น 128.174.5.50 ได้ยาก จึงมีการตั้งค่าทะเบียนชื่อเชิงสัญลักษณ์ไว้ที่ NIC ซึ่งผู้คนจะพูดว่า "ฉันต้องการให้โฮสต์ของฉันชื่อ 'uiucuxc'" เครื่องที่เชื่อมต่อกับอินเทอร์เน็ตทั่วประเทศจะเชื่อมต่อกับ NIC ในช่วงกลางดึก ตรวจสอบวันที่แก้ไขในไฟล์ hosts และหากมีการแก้ไขก็จะย้ายไปยังเครื่องของตนเอง ด้วยการมาถึงของเวิร์กสเตชันและไมโครคอนโทรลเลอร์ การเปลี่ยนแปลงไฟล์ hosts จะต้องทำทุกคืน นอกจากนี้ยังใช้แรงงานมากและสิ้นเปลืองแบนด์วิดท์เครือข่ายมาก RFC-882 และมาตรฐานอื่นๆ อีกหลายฉบับได้อธิบายถึงบริการชื่อโดเมน ซึ่งเป็นระบบฐานข้อมูลแบบกระจายสำหรับการแมปชื่อไปยังที่อยู่

เราต้องมาพิจารณาให้ละเอียดขึ้นอีกหน่อยว่าชื่อนั้นมีความหมายอย่างไรบ้าง ประการแรก โปรดทราบว่าที่อยู่ระบุถึงการเชื่อมต่อเฉพาะบนเครือข่ายเฉพาะ หากเครื่องเคลื่อนย้าย ที่อยู่ก็จะเปลี่ยนไป ประการที่สอง เครื่องหนึ่งอาจมีชื่อได้หนึ่งชื่อหรือมากกว่า และมีที่อยู่เครือข่าย (การเชื่อมต่อ) ได้หนึ่งที่อยู่หรือมากกว่าไปยังเครือข่ายต่างๆ ชื่อชี้ไปยังสิ่งที่มีประโยชน์ในการทำงาน (เช่น เครื่อง) และที่อยู่ IP ชี้ไปยังอินเทอร์เฟซบนผู้ให้บริการนั้น ชื่อเป็นเพียงสัญลักษณ์แทนรายการที่อยู่บนเครือข่าย หากเครื่องย้ายไปยังเครือข่ายอื่น ที่อยู่จะเปลี่ยนไป แต่ชื่ออาจยังคงเหมือนเดิม

ชื่อโดเมนมีโครงสร้างแบบต้นไม้ โดยมีรากของต้นไม้อยู่ทางด้านขวา ตัวอย่างเช่น:

uxc.cso.uiuc.edu

เป็นเครื่องจักรที่เรียกว่า 'uxc' (ซึ่งเป็นชื่อที่กำหนดขึ้นโดยพลการ) ภายในโดเมนย่อยวิธีการจัดสรรของ U of I และ 'uiuc' (มหาวิทยาลัยอิลลินอยส์แห่งเออร์บานา) ซึ่งจดทะเบียนกับ 'edu' (กลุ่มสถาบันการศึกษา)

แบบจำลองอย่างง่ายของการแปลงชื่อโดเมนเป็นชื่อจริงคือ บนเครื่องของผู้ใช้จะมีตัวแปลงชื่อโดเมน (resolver) ตัวแปลงชื่อโดเมนนี้รู้วิธีติดต่อกับเซิร์ฟเวอร์ชื่อโดเมนหลัก (root name server) ผ่านเครือข่าย เซิร์ฟเวอร์ชื่อโดเมนหลักเป็นฐานของระบบการดึงข้อมูลที่มีโครงสร้างแบบต้นไม้ พวกมันรู้ว่าใครเป็นผู้รับผิดชอบในการจัดการโดเมนระดับแรก (เช่น 'edu') การเลือกใช้เซิร์ฟเวอร์ชื่อโดเมนหลักใดนั้นเป็นพารามิเตอร์ในการติดตั้ง จากเซิร์ฟเวอร์ชื่อโดเมนหลัก ตัวแปลงชื่อโดเมนจะค้นหาว่าใครเป็นผู้ให้บริการ 'edu' จากนั้นจะติดต่อกับเซิร์ฟเวอร์ชื่อโดเมน 'edu' ซึ่งจะส่งรายการที่อยู่ของเซิร์ฟเวอร์สำหรับโดเมนย่อย (เช่น 'uiuc') มาให้ การกระทำนี้จะทำซ้ำกับเซิร์ฟเวอร์ของโดเมนย่อยจนกระทั่งโดเมนย่อยสุดท้ายส่งคืนรายการที่อยู่ของอินเทอร์เฟซบนโฮสต์ที่เกี่ยวข้อง จากนั้นเครื่องของผู้ใช้สามารถเลือกได้ว่าจะใช้ที่อยู่ใดในรายการนี้สำหรับการสื่อสาร

-15-

กลุ่มอาจยื่นขอชื่อโดเมนของตนเอง (เช่น 'uiuc' ข้างต้น) โดยวิธีการจะคล้ายกับการจัดสรรที่อยู่ IP ข้อกำหนดเพียงอย่างเดียวคือ ผู้ขอต้องมีเครื่องคอมพิวเตอร์สองเครื่องที่สามารถเข้าถึงได้จากอินเทอร์เน็ต ซึ่งจะทำหน้าที่เป็นเนมเซิร์ฟเวอร์สำหรับโดเมนนั้น เซิร์ฟเวอร์เหล่านั้นยังสามารถทำหน้าที่เป็นเซิร์ฟเวอร์สำหรับซับโดเมน หรืออาจกำหนดให้เซิร์ฟเวอร์อื่นทำหน้าที่ดังกล่าวได้ โปรดทราบว่าเซิร์ฟเวอร์ไม่จำเป็นต้องตั้งอยู่ในสถานที่ใดสถานที่หนึ่งโดยเฉพาะ ตราบใดที่สามารถเข้าถึงได้สำหรับการแก้ไขชื่อ (มหาวิทยาลัยอิลลินอยส์อาจขอให้มหาวิทยาลัยมิชิแกนสเตทดำเนินการแทนก็ได้ และนั่นก็ไม่มีปัญหา) ปัญหาที่ใหญ่ที่สุดคือต้องมีคนคอยบำรุงรักษาฐานข้อมูล หากเครื่องคอมพิวเตอร์ไม่สะดวก การบำรุงรักษาอาจไม่ทันท่วงที สิ่งที่ควรทราบอีกประการหนึ่งคือ เมื่อโดเมนถูกจัดสรรให้กับหน่วยงานบริหารแล้ว หน่วยงานนั้นสามารถจัดสรรซับโดเมนได้อย่างอิสระโดยใช้วิธีการใดก็ได้ตามที่เห็นสมควร

เซิร์ฟเวอร์ Berkeley Internet Name Domain (BIND) ทำหน้าที่จัดการชื่อโดเมนอินเทอร์เน็ตสำหรับระบบ UNIX เซิร์ฟเวอร์ชื่อโดเมนนี้เป็นระบบฐานข้อมูลแบบกระจายที่อนุญาตให้ไคลเอ็นต์ตั้งชื่อทรัพยากรและแบ่งปันข้อมูลนั้นกับโฮสต์เครือข่ายอื่นๆ BIND ถูกรวมเข้ากับ 4.3BSD และใช้ในการค้นหาและจัดเก็บชื่อโฮสต์ ที่อยู่ ตัวแทนอีเมล ข้อมูลโฮสต์ และอื่นๆ โดยจะแทนที่ไฟล์ "/etc/hosts" สำหรับการค้นหาชื่อโฮสต์ BIND ยังคงเป็นโปรแกรมที่กำลังพัฒนาอย่างต่อเนื่อง หากต้องการติดตามรายงานเกี่ยวกับปัญหาการทำงาน การตัดสินใจด้านการออกแบบในอนาคต ฯลฯ โปรดเข้าร่วมรายชื่อผู้รับจดหมายของ BIND โดยส่งคำขอไปที่ "[email protected]" นอกจากนี้ยังสามารถดาวน์โหลด BIND ผ่าน FTP แบบไม่ระบุตัวตนได้จาก ucbarpa.berkley.edu

การใช้ BIND มีข้อดีหลายประการ ข้อดีที่สำคัญที่สุดประการหนึ่งคือ ช่วยให้โฮสต์ไม่ต้องพึ่งพาไฟล์ "/etc/hosts" ว่าจะต้องอัปเดตและสมบูรณ์อยู่เสมอ ภายในโดเมน .uiuc.edu มีเพียงไม่กี่โฮสต์เท่านั้นที่อยู่ในตารางโฮสต์ที่ SRI แจกจ่าย ส่วนที่เหลือจะแสดงอยู่ในตาราง BIND บนเครื่อง uxc.cso.uiuc.edu (เครื่องเซิร์ฟเวอร์สำหรับโดเมน .uiuc.edu ส่วนใหญ่) และสามารถเข้าถึงได้จากโฮสต์อินเทอร์เน็ตอื่นๆ ที่ใช้งาน BIND เช่นกัน

BIND ยังสามารถให้ข้อมูลการส่งต่ออีเมลสำหรับโฮสต์ภายในที่ไม่สามารถเข้าถึงได้โดยตรงจากอินเทอร์เน็ต โฮสต์เหล่านี้อาจอยู่ในเครือข่ายที่ไม่ประกาศ หรือไม่ได้เชื่อมต่อกับเครือข่ายเลย เช่น ในกรณีของโฮสต์ที่เข้าถึงได้ผ่าน UUCP ข้อมูลเพิ่มเติมเกี่ยวกับ BIND มีอยู่ใน "คู่มือการใช้งานเนมเซิร์ฟเวอร์สำหรับ BIND" ใน "คู่มือผู้จัดการระบบ UNIX" เวอร์ชัน 4.3BSD

มีโดเมนพิเศษบางส่วนบนเครือข่าย เช่น SRI-NIC.ARPA โดเมน 'arpa' เป็นโดเมนในอดีต หมายถึงโฮสต์ที่ลงทะเบียนไว้ในฐานข้อมูลโฮสต์เก่าของ NIC นอกจากนี้ยังมีโดเมนในรูปแบบ NNSC.NSF.NET โดเมนพิเศษเหล่านี้ถูกใช้งานอย่างจำกัดและต้องมีการอธิบายเหตุผลอย่างละเอียด โดเมนเหล่านี้หมายถึงเซิร์ฟเวอร์ที่อยู่ภายใต้การควบคุมดูแลของฝ่ายบริหาร

เป็นการจัดการผ่านเครือข่ายมากกว่าองค์กรใดองค์กรหนึ่ง ซึ่งทำให้สามารถย้ายเซิร์ฟเวอร์จริงไปไว้บนเครือข่ายได้ ในขณะที่ส่วนติดต่อผู้ใช้ของเครื่องนั้นยังคงเหมือนเดิม กล่าวคือ หาก BBN สละการควบคุม NNSC ผู้ให้บริการรายใหม่ก็จะยังคงใช้ชื่อนั้นอยู่

ในความเป็นจริง ระบบโดเมนเป็นระบบที่ทั่วไปและซับซ้อนกว่าที่ได้อธิบายไว้มาก ตัวแก้ไขและเซิร์ฟเวอร์บางตัวจะแคชข้อมูลไว้เพื่อให้สามารถข้ามขั้นตอนในการแก้ไขได้ ข้อมูลที่เซิร์ฟเวอร์ให้มานั้นสามารถเป็นข้อมูลใดก็ได้ ไม่ใช่เพียงแค่ที่อยู่ IP เท่านั้น ซึ่งทำให้ระบบนี้สามารถใช้งานได้ทั้งในเครือข่ายที่ไม่ใช้ IP และสำหรับอีเมล ซึ่งอาจจำเป็นต้องให้ข้อมูลเกี่ยวกับตัวเชื่อมต่ออีเมลระดับกลาง

Berkeley Unix มีปัญหาอะไร

มหาวิทยาลัยแคลิฟอร์เนียที่เบิร์กลีย์ได้รับการสนับสนุนด้านเงินทุนจาก DARPA เพื่อปรับปรุงระบบ Unix ในหลายด้าน หนึ่งในนั้นคือการเพิ่มการรองรับโปรโตคอลอินเทอร์เน็ต ในเวอร์ชันก่อนหน้า (เช่น BSD 4.2) มีการรองรับโปรโตคอลอินเทอร์เน็ตพื้นฐาน (TCP, IP, SMTP, ARP) ได้ดี ทำให้สามารถทำงานได้ดีบนเครือข่ายอีเธอร์เน็ต IP และอินเทอร์เน็ตขนาดเล็ก อย่างไรก็ตาม มีข้อบกพร่องเมื่อเชื่อมต่อกับเครือข่ายที่ซับซ้อน ปัญหาเหล่านี้ส่วนใหญ่ได้รับการแก้ไขแล้วในเวอร์ชันล่าสุด (BSD 4.3) เนื่องจากเป็นพื้นฐานที่ผู้จำหน่ายหลายรายใช้ในการพัฒนา Unix (ไม่ว่าจะโดยการดัดแปลงโค้ดที่มีอยู่หรือใช้เป็นแบบจำลอง) การใช้งานหลายอย่าง (เช่น Ultrix) จึงยังคงใช้ BSD 4.2 เป็นพื้นฐาน ดังนั้นจึงยังมีการใช้งานหลายอย่างที่มีปัญหาของ BSD 4.2 อยู่ เมื่อเวลาผ่านไป เมื่อ BSD 4.3 ทยอยออกมาเป็นเวอร์ชันใหม่ ปัญหาหลายอย่างก็จะได้รับการแก้ไข ต่อไปนี้คือรายการของสถานการณ์ปัญหาบางส่วนและวิธีการแก้ไขในแต่ละเวอร์ชัน

การเปลี่ยนเส้นทาง ICMP

ตามแบบจำลองของอินเทอร์เน็ต สิ่งที่ระบบจำเป็นต้องรู้เพื่อเข้าถึงที่ใดก็ได้บนอินเทอร์เน็ตก็คือ ที่อยู่ของตัวเอง ที่อยู่ของปลายทางที่ต้องการไป และวิธีการเข้าถึงเกตเวย์ที่รู้จักอินเทอร์เน็ต ไม่จำเป็นต้องเป็นเกตเวย์ที่ดีที่สุด หากระบบอยู่ในเครือข่ายที่มีเกตเวย์หลายตัว และโฮสต์ส่งแพ็กเก็ตเพื่อส่งไปยังเกตเวย์ที่รู้สึกว่าเกตเวย์ที่เชื่อมต่อโดยตรงอีกตัวหนึ่งเหมาะสมกว่า เกตเวย์จะส่งข้อความไปยังผู้ส่ง ข้อความนี้คือการเปลี่ยนเส้นทาง ICMP ซึ่งบอกอย่างสุภาพว่า "ฉันจะส่งข้อความนี้ให้คุณ แต่คุณควรใช้เกตเวย์นั้นเพื่อเข้าถึงโฮสต์นี้" BSD 4.2 เพิกเฉยต่อข้อความเหล่านี้ ซึ่งจะสร้างภาระให้กับเกตเวย์และเครือข่ายท้องถิ่นมากขึ้น เนื่องจากสำหรับทุกแพ็กเก็ต

-17-

เมื่อส่งแล้ว เกตเวย์จะส่งแพ็กเก็ตกลับไปยังผู้ส่งต้นทาง BSD 4.3 ใช้การเปลี่ยนเส้นทางเพื่ออัปเดตตารางการกำหนดเส้นทาง โดยจะใช้เส้นทางนั้นจนกว่าจะหมดเวลา แล้วจึงกลับไปใช้เส้นทางที่คิดว่าควรใช้ กระบวนการทั้งหมดจะวนซ้ำ แต่ดีกว่าการทำทีละแพ็กเก็ตมาก

รถพ่วง

แอปพลิเคชัน (เช่น FTP) ส่งสตริงของไบต์ไปยัง TCP ซึ่งจะแบ่งสตริงนั้นออกเป็นส่วนๆ และเพิ่มส่วนหัว TCP จากนั้น TCP จะส่งบล็อกข้อมูลไปยัง IP ซึ่งจะเพิ่มส่วนหัวของตัวเองและส่งแพ็กเก็ตผ่านเครือข่าย การเพิ่มส่วนหัวให้กับข้อมูลทั้งหมดนี้ทำให้เกิดการเปลี่ยนแปลงหน่วยความจำทั้งในเครื่องส่งและเครื่องรับ มีคนคิดว่าถ้าแพ็กเก็ตยาวและเพิ่มส่วนหัวไว้ที่ท้าย (กลายเป็นส่วนท้ายแพ็กเก็ต) เครื่องรับสามารถวางแพ็กเก็ตไว้ที่จุดเริ่มต้นของขอบเขตหน้า และถ้าส่วนท้ายแพ็กเก็ตถูกต้อง ก็สามารถลบส่วนท้ายออกและถ่ายโอนการควบคุมหน้าโดยไม่ต้องเปลี่ยนแปลงหน่วยความจำ ปัญหาคือส่วนท้ายแพ็กเก็ตไม่เคยมีการกำหนดมาตรฐาน และเกตเวย์ส่วนใหญ่ไม่รู้ว่าจะต้องมองหาข้อมูลการกำหนดเส้นทางที่ส่วนท้ายของบล็อก เมื่อใช้ส่วนท้ายแพ็กเก็ต เครื่องมักจะทำงานได้ดีในเครือข่ายท้องถิ่น (ไม่มีเกตเวย์เกี่ยวข้อง) และสำหรับบล็อกสั้นๆ ผ่านเกตเวย์ (ซึ่งไม่ได้ใช้ส่วนท้ายแพ็กเก็ต) ดังนั้น การใช้งาน TELNET และ FTP สำหรับไฟล์ขนาดสั้นมากจึงทำงานได้ดี แต่การใช้งาน FTP สำหรับไฟล์ขนาดใหญ่ดูเหมือนจะค้าง ใน BSD 4.2 ตัวเลือก trailers เป็นตัวเลือกในการบูต และควรตรวจสอบให้แน่ใจว่าได้ปิดใช้งานเมื่อใช้งานอินเทอร์เน็ต ส่วน BSD 4.3 จะเจรจาเรื่อง trailers เอง ดังนั้นจึงใช้ trailers บนเครือข่ายภายใน และจะไม่ใช้เมื่อใช้งานผ่านเครือข่ายภายนอก

การออกอากาศ

TCP จะส่งบล็อกข้อมูลไปยังคู่สนทนาที่ปลายอีกด้านของการเชื่อมต่อ หากไม่ได้รับการยืนยันภายในระยะเวลาที่เหมาะสม มันจะส่งบล็อกข้อมูลนั้นซ้ำ การพิจารณาว่าระยะเวลาใดเหมาะสมนั้นทำโดยอัลกอริทึมการส่งซ้ำของ TCP ไม่มีอัลกอริทึมใดที่ถูกต้องที่สุด แต่บางอัลกอริทึมก็ดีกว่าอัลกอริทึมอื่นๆ โดยวัดจากจำนวนการส่งซ้ำที่ไม่จำเป็น BSD 4.2 มีอัลกอริทึมการส่งซ้ำที่ส่งซ้ำอย่างรวดเร็วและบ่อยครั้ง ซึ่งเป็นสิ่งที่คุณต้องการหากคุณมีเครื่องจำนวนมากบนเครือข่ายอีเธอร์เน็ต (เครือข่ายที่มีความล่าช้าต่ำและแบนด์วิดท์สูง) หากคุณมีเครือข่ายที่มีความล่าช้าค่อนข้างสูงและแบนด์วิดท์จำกัด (เช่น สาย 56kb) มันมักจะส่งซ้ำอย่างรุนแรงเกินไป ดังนั้นจึงทำให้เครือข่ายและเกตเวย์ส่งผ่านปริมาณการรับส่งข้อมูลมากกว่าที่จำเป็นสำหรับการสนทนาในแต่ละครั้ง อัลกอริทึมการส่งซ้ำจะปรับตัวให้เข้ากับความล่าช้าของเครือข่าย

หลังจากส่งแพ็กเก็ตไปไม่กี่แพ็กเก็ต แต่ BSD 4.2 ปรับตัวได้ช้าในสถานการณ์ที่มีความล่าช้า BSD 4.3 ทำได้ดีกว่ามากและพยายามทำให้ดีที่สุดสำหรับทั้งสองสถานการณ์ มันจะส่งการส่งซ้ำอย่างรวดเร็วหากอยู่ในเครือข่ายที่มีความล่าช้าต่ำ จากนั้นก็จะหยุดส่งอย่างรวดเร็ว นอกจากนี้ยังอนุญาตให้มีความล่าช้าได้ประมาณ 4 นาทีก่อนที่จะยอมแพ้และประกาศว่าการเชื่อมต่อขาด

ใบอนุญาต Project Gutenberg™ ฉบับเต็ม

โปรดอ่านข้อความนี้ก่อนเผยแพร่หรือใช้งานผลงานนี้
เพื่อปกป้องพันธกิจของ Project Gutenberg™ ในการส่งเสริมการเผยแพร่ผลงานอิเล็กทรอนิกส์อย่างเสรี การใช้หรือเผยแพร่ผลงานนี้ (หรือผลงานอื่นใดที่เกี่ยวข้องกับวลี “Project Gutenberg” ไม่ว่าในทางใดก็ตาม) ถือว่าคุณตกลงที่จะปฏิบัติตามข้อกำหนดทั้งหมดของสัญญาอนุญาตฉบับเต็มของ Project Gutenberg ซึ่งมีอยู่ในไฟล์นี้หรือทางออนไลน์ที่ www.gutenberg.org/license
ส่วนที่ 1. ข้อกำหนดทั่วไปในการใช้งานและการเผยแพร่ผลงานอิเล็กทรอนิกส์ของโครงการ Gutenberg
1.A. การอ่านหรือใช้งานส่วนใดส่วนหนึ่งของงานอิเล็กทรอนิกส์ของ Project Gutenberg นี้ แสดงว่าคุณได้อ่าน เข้าใจ ตกลง และยอมรับข้อกำหนดทั้งหมดของข้อตกลงใบอนุญาตและข้อตกลงทรัพย์สินทางปัญญา (เครื่องหมายการค้า/ลิขสิทธิ์) นี้แล้ว หากคุณไม่เห็นด้วยที่จะปฏิบัติตามข้อกำหนดทั้งหมดของข้อตกลงนี้ คุณต้องหยุดใช้งานและส่งคืนหรือทำลายสำเนาทั้งหมดของงานอิเล็กทรอนิกส์ของ Project Gutenberg ที่อยู่ในครอบครองของคุณ หากคุณชำระค่าธรรมเนียมเพื่อขอรับสำเนาหรือเข้าถึงงานอิเล็กทรอนิกส์ของ Project Gutenberg และคุณไม่เห็นด้วยที่จะผูกพันตามข้อกำหนดของข้อตกลงนี้ คุณสามารถขอรับเงินคืนได้จากบุคคลหรือนิติบุคคลที่คุณชำระค่าธรรมเนียมให้ ตามที่ระบุไว้ในข้อ 1.E.8
1.B. “Project Gutenberg” เป็นเครื่องหมายการค้าจดทะเบียน ผู้ที่สามารถใช้หรือเกี่ยวข้องกับงานอิเล็กทรอนิกส์ใดๆ ได้นั้น ต้องยินยอมปฏิบัติตามข้อตกลงนี้เท่านั้น แม้ว่าจะไม่ปฏิบัติตามข้อตกลงนี้อย่างครบถ้วน ก็ยังสามารถทำบางสิ่งบางอย่างกับงานอิเล็กทรอนิกส์ส่วนใหญ่ของ Project Gutenberg ได้ โปรดดูรายละเอียดในข้อ 1.C ด้านล่าง และหากคุณปฏิบัติตามข้อตกลงนี้และช่วยรักษาการเข้าถึงงานอิเล็กทรอนิกส์ของ Project Gutenberg ในอนาคตโดยไม่เสียค่าใช้จ่าย ก็ยังสามารถทำสิ่งต่างๆ ได้มากมาย โปรดดูรายละเอียดในข้อ 1.E ด้านล่าง
1.C. มูลนิธิ Project Gutenberg Literary Archive Foundation (“มูลนิธิ” หรือ PGLAF) เป็นเจ้าของลิขสิทธิ์ในการรวบรวมผลงานอิเล็กทรอนิกส์ของ Project Gutenberg ผลงานเกือบทั้งหมดในคอลเลกชันนี้เป็นสาธารณสมบัติในสหรัฐอเมริกา หากผลงานใดไม่ได้รับการคุ้มครองโดยกฎหมายลิขสิทธิ์ในสหรัฐอเมริกา และคุณอยู่ในสหรัฐอเมริกา เราไม่มีสิทธิ์ที่จะห้ามคุณจากการคัดลอก แจกจ่าย แสดง หรือสร้างผลงานดัดแปลงจากผลงานนั้น ตราบใดที่ได้ลบการอ้างอิงถึง Project Gutenberg ออกทั้งหมดแล้ว แน่นอนว่า เราหวังว่าคุณจะสนับสนุนภารกิจของ Project Gutenberg ในการส่งเสริมการเข้าถึงผลงานอิเล็กทรอนิกส์อย่างเสรี โดยการแบ่งปันผลงานของ Project Gutenberg อย่างเสรีตามข้อตกลงนี้ และคงชื่อ Project Gutenberg ไว้กับผลงานนั้น คุณสามารถปฏิบัติตามข้อตกลงนี้ได้ง่ายๆ โดยการเก็บรักษาผลงานนี้ในรูปแบบเดิมพร้อมกับใบอนุญาต Project Gutenberg ฉบับเต็มที่แนบมาด้วย เมื่อคุณแบ่งปันผลงานนั้นกับผู้อื่นโดยไม่คิดค่าใช้จ่าย
งานชิ้นนี้เป็นหนึ่งในงานไม่กี่ชิ้นที่ได้รับการคุ้มครองโดยกฎหมายลิขสิทธิ์ในสหรัฐอเมริกาและประเทศส่วนใหญ่ทั่วโลก โดยรวมอยู่ในคอลเลกชันของ Project Gutenberg ด้วยความยินยอมจากเจ้าของลิขสิทธิ์ ข้อมูลเกี่ยวกับเจ้าของลิขสิทธิ์สำหรับงานชิ้นนี้และเงื่อนไขการใช้งานที่เจ้าของลิขสิทธิ์กำหนดไว้สำหรับงานชิ้นนี้ได้ระบุไว้ในตอนต้นของงานชิ้นนี้แล้ว
1.D. กฎหมายลิขสิทธิ์ของประเทศที่คุณอยู่จะควบคุมสิ่งที่คุณสามารถทำได้กับงานนี้ กฎหมายลิขสิทธิ์ในประเทศส่วนใหญ่มีการเปลี่ยนแปลงอยู่ตลอดเวลา หากคุณอยู่นอกสหรัฐอเมริกา โปรดตรวจสอบกฎหมายของประเทศของคุณเพิ่มเติมจากข้อกำหนดของข้อตกลงนี้ก่อนที่จะดาวน์โหลด คัดลอก แสดง แสดงผล แจกจ่าย หรือสร้างงานดัดแปลงจากงานนี้หรืองานอื่นใดของ Project Gutenberg มูลนิธิไม่มีการรับรองใด ๆ เกี่ยวกับสถานะลิขสิทธิ์ของงานใด ๆ ในประเทศอื่นนอกเหนือจากสหรัฐอเมริกา
1.E. เว้นแต่คุณได้ลบข้อมูลอ้างอิงทั้งหมดถึง Project Gutenberg แล้ว:
1.E.1. ประโยคต่อไปนี้ พร้อมลิงก์ที่ใช้งานได้ หรือการเข้าถึงโดยตรงไปยังสัญญาอนุญาตโครงการกูเทนเบิร์กฉบับเต็ม จะต้องปรากฏอย่างเด่นชัดทุกครั้งที่มีการเข้าถึง แสดง เล่น ดู คัดลอก หรือแจกจ่ายสำเนาใด ๆ ของงานโครงการกูเทนเบิร์ก (งานใด ๆ ที่มีวลี “โครงการกูเทนเบิร์ก” ปรากฏอยู่ หรือที่เกี่ยวข้องกับวลี “โครงการกูเทนเบิร์ก”):
อีบุ๊กเล่มนี้เปิดให้ทุกคนทุกที่ในสหรัฐอเมริกาและส่วนใหญ่ของโลกใช้งานได้ฟรีโดยแทบไม่มีข้อจำกัดใดๆ คุณสามารถคัดลอก แจกจ่าย หรือนำไปใช้ซ้ำได้ภายใต้เงื่อนไขของสัญญาอนุญาต Project Gutenberg™ ที่รวมอยู่ในอีบุ๊กเล่มนี้หรือทางออนไลน์ที่www.gutenberg.orgหากคุณไม่ได้อยู่ในสหรัฐอเมริกา คุณจะต้องตรวจสอบกฎหมายของประเทศที่คุณอยู่ก่อนที่จะใช้อีบุ๊กเล่มนี้
1.E.2. หากผลงานอิเล็กทรอนิกส์ของ Project Gutenberg แต่ละชิ้นนั้นดัดแปลงมาจากข้อความที่ไม่ได้รับการคุ้มครองโดยกฎหมายลิขสิทธิ์ของสหรัฐอเมริกา (ไม่มีข้อความระบุว่าเผยแพร่โดยได้รับอนุญาตจากเจ้าของลิขสิทธิ์) ผลงานนั้นสามารถคัดลอกและเผยแพร่ให้กับบุคคลใดก็ได้ในสหรัฐอเมริกาโดยไม่ต้องเสียค่าธรรมเนียมหรือค่าใช้จ่ายใดๆ หากคุณกำลังเผยแพร่หรือให้สิทธิ์เข้าถึงผลงานที่มีวลี “Project Gutenberg” เกี่ยวข้องหรือปรากฏอยู่ในผลงานนั้น คุณต้องปฏิบัติตามข้อกำหนดในย่อหน้า 1.E.1 ถึง 1.E.7 หรือขออนุญาตใช้ผลงานและเครื่องหมายการค้า Project Gutenberg ตามที่ระบุไว้ในย่อหน้า 1.E.8 หรือ 1.E.9
1.E.3. หากผลงานอิเล็กทรอนิกส์ของ Project Gutenberg ชิ้นใดชิ้นหนึ่งถูกเผยแพร่โดยได้รับอนุญาตจากเจ้าของลิขสิทธิ์ การใช้งานและการเผยแพร่ของคุณจะต้องเป็นไปตามข้อ 1.E.1 ถึง 1.E.7 และข้อกำหนดเพิ่มเติมใดๆ ที่เจ้าของลิขสิทธิ์กำหนดไว้ ข้อกำหนดเพิ่มเติมจะเชื่อมโยงไปยังสัญญาอนุญาตของ Project Gutenberg สำหรับผลงานทั้งหมดที่เผยแพร่โดยได้รับอนุญาตจากเจ้าของลิขสิทธิ์ ซึ่งสามารถดูได้ที่ส่วนต้นของเอกสารนี้
1.E.4. ห้ามยกเลิกการเชื่อมโยง แยก หรือนำข้อกำหนดทั้งหมดของสัญญาอนุญาตโครงการกูเทนเบิร์กออกจากงานนี้ หรือไฟล์ใดๆ ที่มีส่วนหนึ่งของงานนี้ หรืองานอื่นๆ ที่เกี่ยวข้องกับโครงการกูเทนเบิร์ก

1.E.6. คุณสามารถแปลงและเผยแพร่ผลงานนี้ในรูปแบบไบนารี รูปแบบบีบอัด รูปแบบที่มีเครื่องหมายกำกับ รูปแบบที่ไม่ใช่กรรมสิทธิ์ หรือรูปแบบกรรมสิทธิ์ใดๆ ก็ได้ รวมถึงรูปแบบการประมวลผลคำหรือไฮเปอร์เท็กซ์ อย่างไรก็ตาม หากคุณให้สิทธิ์การเข้าถึงหรือเผยแพร่สำเนาผลงานของ Project Gutenberg ในรูปแบบอื่นนอกเหนือจาก “Plain Vanilla ASCII” หรือรูปแบบอื่นๆ ที่ใช้ในเวอร์ชันอย่างเป็นทางการที่โพสต์บนเว็บไซต์อย่างเป็นทางการของ Project Gutenberg (www.gutenberg.org) คุณต้องจัดหาสำเนา วิธีการส่งออกสำเนา หรือวิธีการขอรับสำเนาตามคำขอของผลงานในรูปแบบ “Plain Vanilla ASCII” หรือรูปแบบอื่นๆ ดั้งเดิม โดยไม่มีค่าใช้จ่าย ค่าธรรมเนียม หรือค่าใช้จ่ายเพิ่มเติมใดๆ แก่ผู้ใช้ รูปแบบทางเลือกใดๆ ต้องมีข้อตกลงใบอนุญาต Project Gutenberg ฉบับเต็มตามที่ระบุไว้ในย่อหน้า 1.E.1
1.E.7. ห้ามเรียกเก็บค่าธรรมเนียมสำหรับการเข้าถึง การดู การแสดง การแสดงผล การคัดลอก หรือการแจกจ่ายผลงานใดๆ ของ Project Gutenberg เว้นแต่คุณจะปฏิบัติตามวรรค 1.E.8 หรือ 1.E.9
1.E.8. คุณสามารถเรียกเก็บค่าธรรมเนียมที่สมเหตุสมผลสำหรับการทำสำเนา การให้สิทธิ์เข้าถึง หรือการแจกจ่ายผลงานอิเล็กทรอนิกส์ของ Project Gutenberg ได้ โดยมีเงื่อนไขดังนี้:
  • • คุณต้องชำระค่าลิขสิทธิ์ 20% ของกำไรขั้นต้นที่คุณได้รับจากการใช้ผลงานของ Project Gutenberg โดยคำนวณด้วยวิธีเดียวกับที่คุณใช้ในการคำนวณภาษีอยู่แล้ว ค่าธรรมเนียมนี้ต้องจ่ายให้กับเจ้าของเครื่องหมายการค้า Project Gutenberg แต่เขาตกลงที่จะบริจาคค่าลิขสิทธิ์ตามวรรคนี้ให้กับมูลนิธิ Project Gutenberg Literary Archive Foundation การชำระค่าลิขสิทธิ์ต้องชำระภายใน 60 วันนับจากวันที่คุณจัดทำ (หรือมีหน้าที่ตามกฎหมายที่จะต้องจัดทำ) แบบแสดงรายการภาษีรายงวด การชำระค่าลิขสิทธิ์ควรระบุอย่างชัดเจนว่าเป็นค่าลิขสิทธิ์ และส่งไปยังมูลนิธิ Project Gutenberg Literary Archive Foundation ตามที่อยู่ที่ระบุไว้ในหัวข้อ 4 “ข้อมูลเกี่ยวกับการบริจาคให้กับมูลนิธิ Project Gutenberg Literary Archive Foundation”
  • • คุณต้องคืนเงินเต็มจำนวนแก่ผู้ใช้ที่แจ้งเป็นลายลักษณ์อักษร (หรือทางอีเมล) ภายใน 30 วันนับจากวันที่ได้รับสินค้าว่าไม่เห็นด้วยกับข้อกำหนดของสัญญาอนุญาตใช้สิทธิ์ Project Gutenberg™ ฉบับเต็ม คุณต้องขอให้ผู้ใช้ดังกล่าวส่งคืนหรือทำลายสำเนาทั้งหมดของผลงานที่อยู่ในรูปแบบสื่อทางกายภาพ และยุติการใช้งานและการเข้าถึงสำเนาอื่นๆ ของผลงาน Project Gutenberg™ ทั้งหมด
  • • คุณจะต้องคืนเงินเต็มจำนวนที่ชำระไปสำหรับงานนั้น หรือส่งสำเนาใหม่ให้ หากพบข้อบกพร่องในงานอิเล็กทรอนิกส์ และแจ้งให้คุณทราบภายใน 90 วันนับจากวันที่ได้รับงาน ตามวรรค 1.F.3
  • • คุณต้องปฏิบัติตามข้อกำหนดอื่นๆ ทั้งหมดของข้อตกลงนี้สำหรับการเผยแพร่ผลงานของ Project Gutenberg™ โดยไม่คิดค่าใช้จ่าย
1.E.9. หากท่านประสงค์จะเรียกเก็บค่าธรรมเนียมหรือเผยแพร่ผลงานอิเล็กทรอนิกส์หรือกลุ่มผลงานของ Project Gutenberg™ ภายใต้เงื่อนไขที่แตกต่างจากที่ระบุไว้ในข้อตกลงนี้ ท่านต้องขออนุญาตเป็นลายลักษณ์อักษรจากมูลนิธิ Project Gutenberg Literary Archive Foundation ซึ่งเป็นผู้ดูแลเครื่องหมายการค้า Project Gutenberg™ โปรดติดต่อมูลนิธิตามที่ระบุไว้ในส่วนที่ 3 ด้านล่าง
1.ฟ.
1.F.1. อาสาสมัครและพนักงานของ Project Gutenberg ทุ่มเทความพยายามอย่างมากในการระบุ ค้นคว้าข้อมูลลิขสิทธิ์ ถอดความ และตรวจทานผลงานที่ไม่ได้รับการคุ้มครองโดยกฎหมายลิขสิทธิ์ของสหรัฐอเมริกา ในการสร้างคอลเลกชันของ Project Gutenberg™ อย่างไรก็ตาม แม้จะพยายามอย่างเต็มที่แล้ว ผลงานอิเล็กทรอนิกส์ของ Project Gutenberg™ และสื่อที่ใช้จัดเก็บ อาจมี “ข้อบกพร่อง” เช่น ข้อมูลที่ไม่สมบูรณ์ ไม่ถูกต้อง หรือเสียหาย ข้อผิดพลาดในการถอดความ การละเมิดลิขสิทธิ์หรือทรัพย์สินทางปัญญาอื่นๆ ดิสก์หรือสื่ออื่นๆ ที่ชำรุดหรือเสียหาย ไวรัสคอมพิวเตอร์ หรือรหัสคอมพิวเตอร์ที่ทำให้เกิดความเสียหายหรือไม่สามารถอ่านได้โดยอุปกรณ์ของคุณ
1.F.2. การรับประกันแบบจำกัด การปฏิเสธความรับผิดต่อความเสียหาย - ยกเว้น “สิทธิ์ในการเปลี่ยนหรือคืนเงิน” ที่อธิบายไว้ในย่อหน้า 1.F.3 มูลนิธิ Project Gutenberg Literary Archive Foundation เจ้าของเครื่องหมายการค้า Project Gutenberg™ และบุคคลอื่นใดที่เผยแพร่ผลงานอิเล็กทรอนิกส์ของ Project Gutenberg™ ภายใต้ข้อตกลงนี้ ขอปฏิเสธความรับผิดต่อคุณสำหรับความเสียหาย ค่าใช้จ่าย และค่าธรรมเนียมต่างๆ รวมถึงค่าธรรมเนียมทางกฎหมาย คุณตกลงว่าคุณไม่มีสิทธิ์เรียกร้องใดๆ สำหรับความประมาทเลินเล่อ ความรับผิดโดยเคร่งครัด การละเมิดการรับประกัน หรือการละเมิดสัญญา ยกเว้นที่ระบุไว้ในย่อหน้า 1.F.3 คุณตกลงว่ามูลนิธิ เจ้าของเครื่องหมายการค้า และผู้จัดจำหน่ายใดๆ ภายใต้ข้อตกลงนี้ จะไม่รับผิดชอบต่อคุณสำหรับความเสียหายที่เกิดขึ้นจริง โดยตรง โดยอ้อม ผลกระทบต่อเนื่อง การลงโทษ หรือความเสียหายที่เกิดขึ้นโดยบังเอิญ แม้ว่าคุณจะแจ้งให้ทราบถึงความเป็นไปได้ของความเสียหายดังกล่าวแล้วก็ตาม
1.F.3. สิทธิ์ในการเปลี่ยนหรือคืนเงินที่จำกัด - หากคุณพบข้อบกพร่องในงานอิเล็กทรอนิกส์นี้ภายใน 90 วันนับจากวันที่ได้รับ คุณสามารถขอรับเงินคืน (ถ้ามี) ที่คุณชำระไปได้ โดยส่งคำอธิบายเป็นลายลักษณ์อักษรไปยังบุคคลที่คุณได้รับงานนั้น หากคุณได้รับงานในรูปแบบสื่อทางกายภาพ คุณต้องส่งคืนสื่อนั้นพร้อมกับคำอธิบายเป็นลายลักษณ์อักษร บุคคลหรือหน่วยงานที่จัดหาผลงานที่ชำรุดให้แก่คุณอาจเลือกที่จะจัดหาสำเนาใหม่แทนการคืนเงิน หากคุณได้รับงานในรูปแบบอิเล็กทรอนิกส์ บุคคลหรือหน่วยงานที่จัดหาให้คุณอาจเลือกที่จะให้โอกาสครั้งที่สองแก่คุณในการรับงานในรูปแบบอิเล็กทรอนิกส์แทนการคืนเงิน หากสำเนาที่สองยังชำรุด คุณสามารถเรียกร้องเงินคืนเป็นลายลักษณ์อักษรได้โดยไม่ต้องมีโอกาสแก้ไขปัญหาเพิ่มเติม
1.F.4. นอกเหนือจากสิทธิ์ในการเปลี่ยนหรือคืนเงินที่จำกัดตามที่ระบุไว้ในย่อหน้า 1.F.3 แล้ว งานนี้จัดให้แก่คุณ "ตามสภาพที่เป็นอยู่" โดยไม่มีการรับประกันอื่นใด ไม่ว่าโดยชัดแจ้งหรือโดยนัย รวมถึงแต่ไม่จำกัดเพียงการรับประกันความสามารถในการจำหน่ายหรือความเหมาะสมสำหรับวัตถุประสงค์ใดๆ
1.F.5. บางรัฐไม่อนุญาตให้มีการยกเว้นการรับประกันโดยนัยบางประการ หรือการยกเว้นหรือจำกัดความเสียหายบางประเภท หากการยกเว้นหรือข้อจำกัดใดๆ ที่ระบุไว้ในข้อตกลงนี้ขัดต่อกฎหมายของรัฐที่ใช้บังคับกับข้อตกลงนี้ ข้อตกลงนี้จะถูกตีความเพื่อให้มีการยกเว้นหรือข้อจำกัดสูงสุดตามที่กฎหมายของรัฐนั้นอนุญาต ความเป็นโมฆะหรือไม่สามารถบังคับใช้ได้ของข้อกำหนดใดๆ ในข้อตกลงนี้จะไม่ทำให้ข้อกำหนดที่เหลืออยู่เป็นโมฆะ
1.F.6. การชดใช้ค่าเสียหาย - คุณตกลงที่จะชดใช้และปกป้องมูลนิธิ เจ้าของเครื่องหมายการค้า ตัวแทนหรือพนักงานของมูลนิธิ บุคคลใดก็ตามที่จัดทำสำเนาผลงานอิเล็กทรอนิกส์ของ Project Gutenberg™ ตามข้อตกลงนี้ และอาสาสมัครใดๆ ที่เกี่ยวข้องกับการผลิต การส่งเสริม และการเผยแพร่ผลงานอิเล็กทรอนิกส์ของ Project Gutenberg™ จากความรับผิด ค่าใช้จ่าย และค่าธรรมเนียมทั้งหมด รวมถึงค่าธรรมเนียมทางกฎหมาย ที่เกิดขึ้นโดยตรงหรือโดยอ้อมจากสิ่งต่อไปนี้ที่คุณกระทำหรือก่อให้เกิดขึ้น: (ก) การเผยแพร่ผลงานนี้หรือผลงานใดๆ ของ Project Gutenberg (ข) การเปลี่ยนแปลง แก้ไข เพิ่มเติม หรือลบผลงานใดๆ ของ Project Gutenberg และ (ค) ข้อบกพร่องใดๆ ที่คุณก่อขึ้น
ส่วนที่ 2 ข้อมูลเกี่ยวกับพันธกิจของโครงการกูเตนเบิร์ก
โครงการกูเตนเบิร์ก (Project Gutenberg) มีความหมายเหมือนกันกับการแจกจ่ายผลงานอิเล็กทรอนิกส์ฟรีในรูปแบบที่คอมพิวเตอร์หลากหลายประเภทสามารถอ่านได้ ไม่ว่าจะเป็นคอมพิวเตอร์รุ่นเก่า รุ่นใหม่ หรือคอมพิวเตอร์ที่ใช้งานมานานแล้ว โครงการนี้เกิดขึ้นได้จากความพยายามของอาสาสมัครหลายร้อยคนและการบริจาคจากผู้คนทุกสาขาอาชีพ
อาสาสมัครและการสนับสนุนทางการเงินเพื่อช่วยเหลืออาสาสมัครเป็นสิ่งสำคัญยิ่งต่อการบรรลุเป้าหมายของโครงการกูเตนเบิร์ก และการทำให้มั่นใจว่าคอลเลกชันของโครงการกูเตนเบิร์กจะยังคงเปิดให้ใช้งานได้ฟรีสำหรับคนรุ่นต่อๆ ไป ในปี 2544 มูลนิธิหอจดหมายเหตุวรรณกรรมโครงการกูเตนเบิร์ก (Project Gutenberg Literary Archive Foundation) ได้ถูกก่อตั้งขึ้นเพื่อให้มีอนาคตที่มั่นคงและถาวรสำหรับโครงการกูเตนเบิร์กและคนรุ่นหลัง หากต้องการเรียนรู้เพิ่มเติมเกี่ยวกับมูลนิธิหอจดหมายเหตุวรรณกรรมโครงการกูเตนเบิร์ก และวิธีที่ความพยายามและการบริจาคของคุณสามารถช่วยได้ โปรดดูส่วนที่ 3 และ 4 และหน้าข้อมูลของมูลนิธิที่ www.gutenberg.org
ส่วนที่ 3 ข้อมูลเกี่ยวกับมูลนิธิหอจดหมายเหตุวรรณกรรมโปรเจกต์กูเตนเบิร์ก
มูลนิธิ Project Gutenberg Literary Archive Foundation เป็นองค์กรการศึกษาที่ไม่แสวงหาผลกำไรตามมาตรา 501(c)(3) ของรัฐมิสซิสซิปปี และได้รับการยกเว้นภาษีจากกรมสรรพากรของสหรัฐอเมริกา หมายเลขประจำตัวผู้เสียภาษีของมูลนิธิ (EIN) คือ 64-6221541 การบริจาคให้แก่มูลนิธิ Project Gutenberg Literary Archive Foundation สามารถนำไปหักลดหย่อนภาษีได้เต็มจำนวนตามที่กฎหมายของรัฐบาลกลางสหรัฐอเมริกาและกฎหมายของรัฐของคุณอนุญาต
สำนักงานธุรกิจของมูลนิธิตั้งอยู่ที่ 41 Watchung Plaza #516, Montclair NJ 07042, USA, +1 (862) 621-9288 สามารถดูลิงก์ติดต่อทางอีเมลและข้อมูลการติดต่อล่าสุดได้ที่เว็บไซต์ของมูลนิธิและหน้าอย่างเป็นทางการที่ www.gutenberg.org/contact
ส่วนที่ 4 ข้อมูลเกี่ยวกับการบริจาคให้แก่ มูลนิธิโครงการเก็บรักษาเอกสารวรรณกรรมกูเตนเบิร์ก
โครงการ Project Gutenberg™ ขึ้นอยู่กับการสนับสนุนและการบริจาคจากสาธารณชนอย่างกว้างขวาง และไม่สามารถอยู่รอดได้หากปราศจากการสนับสนุนดังกล่าว เพื่อดำเนินภารกิจในการเพิ่มจำนวนผลงานที่เป็นสาธารณสมบัติและผลงานที่ได้รับอนุญาต ซึ่งสามารถเผยแพร่ได้อย่างอิสระในรูปแบบที่เครื่องอ่านได้ และเข้าถึงได้โดยอุปกรณ์หลากหลายประเภท รวมถึงอุปกรณ์ที่ล้าสมัย การบริจาคจำนวนเล็กน้อย (ตั้งแต่ 1 ถึง 5,000 ดอลลาร์) มีความสำคัญอย่างยิ่งต่อการรักษาสถานะการยกเว้นภาษีกับกรมสรรพากร
มูลนิธิฯ มุ่งมั่นที่จะปฏิบัติตามกฎหมายที่ควบคุมองค์กรการกุศลและการบริจาคเพื่อการกุศลในทั้ง 50 รัฐของสหรัฐอเมริกา ข้อกำหนดในการปฏิบัติตามกฎหมายนั้นไม่เหมือนกัน และต้องใช้ความพยายามอย่างมาก เอกสารจำนวนมาก และค่าธรรมเนียมมากมายเพื่อให้เป็นไปตามข้อกำหนดเหล่านี้ เราจะไม่ขอรับบริจาคในสถานที่ที่เราไม่ได้รับการยืนยันเป็นลายลักษณ์อักษรว่าปฏิบัติตามกฎหมายแล้ว หากต้องการส่งเงินบริจาคหรือตรวจสอบสถานะการปฏิบัติตามกฎหมายของรัฐใดรัฐหนึ่ง โปรดไปที่ www.gutenberg.org/donate
แม้ว่าเราจะไม่สามารถและไม่ขอรับเงินบริจาคจากรัฐที่เราไม่ผ่านข้อกำหนดในการขอรับเงินบริจาค แต่เราไม่ทราบว่ามีข้อห้ามใด ๆ ในการรับเงินบริจาคโดยไม่ได้รับการร้องขอจากผู้บริจาคในรัฐเหล่านั้นที่ติดต่อเราเข้ามาเพื่อเสนอตัวบริจาค
เรายินดีรับเงินบริจาคจากต่างประเทศ แต่เราไม่สามารถให้ข้อมูลใดๆ เกี่ยวกับการเสียภาษีของเงินบริจาคที่ได้รับจากนอกสหรัฐอเมริกาได้ เนื่องจากกฎหมายของสหรัฐอเมริกาเพียงอย่างเดียวก็ครอบคลุมภาระงานของเจ้าหน้าที่จำนวนน้อยของเราแล้ว
โปรดตรวจสอบหน้าเว็บของ Project Gutenberg เพื่อดูวิธีการบริจาคและที่อยู่ในการรับบริจาคในปัจจุบัน เรารับบริจาคหลายวิธี เช่น เช็ค การชำระเงินออนไลน์ และการบริจาคผ่านบัตรเครดิต หากต้องการบริจาค โปรดไปที่: www.gutenberg.org/donate
ส่วนที่ 5 ข้อมูลทั่วไปเกี่ยวกับผลงานอิเล็กทรอนิกส์ของโครงการกูเตนเบิร์ก
ศาสตราจารย์ไมเคิล เอส. ฮาร์ท เป็นผู้ริเริ่มแนวคิดโครงการกูเตนเบิร์ก (Project Gutenberg) ซึ่งเป็นห้องสมุดผลงานอิเล็กทรอนิกส์ที่สามารถแบ่งปันได้อย่างอิสระกับทุกคน ตลอดระยะเวลาสี่สิบปี เขาผลิตและเผยแพร่หนังสืออิเล็กทรอนิกส์ของโครงการกูเตนเบิร์กโดยอาศัยเพียงเครือข่ายอาสาสมัครที่ไม่เป็นทางการเท่านั้น
อีบุ๊กของ Project Gutenberg มักสร้างขึ้นจากหนังสือฉบับพิมพ์หลายเล่ม ซึ่งได้รับการยืนยันแล้วว่าไม่ได้รับการคุ้มครองลิขสิทธิ์ในสหรัฐอเมริกา เว้นแต่จะมีการระบุข้อความแจ้งลิขสิทธิ์ไว้ ดังนั้น เราจึงไม่จำเป็นต้องรักษาความถูกต้องตามข้อกำหนดของหนังสือฉบับพิมพ์เล่มใดเล่มหนึ่งโดยเฉพาะ
คนส่วนใหญ่เริ่มต้นที่เว็บไซต์ของเรา ซึ่งมีระบบค้นหา PG หลักอยู่ที่ www.gutenberg.org
